# arcmemory-datasource-ingestion

## Inspiration

Connectors give an agent hands, but connected data lands nowhere useful. The 2026-08-04 connector-extensions work reaches Slack, Drive, Dropbox, mail, calendar, Notion, S3 — yet a connected source is inert until its content is routed to the right store and can come back out in a turn. Three pressures landed together. First, not everything belongs in memory: a five-year S3 bucket must be searchable in place, not ingested, and an invoice is an exact lookup, not a similarity match. Second, arcmemory already owns capture, consolidation, and recall — so it is the natural brain to decide where connected content lives and how it returns. Third, Josh needs it personally: "I add Slack, I get that channel's history ingested, searchable, kept updated; I add Dropbox or S3, it maps the files so it knows what's there and can use them in a turn."

## Projects

The arcmemory-side ingestion + routing + retrieval layer that sits on top of the connectors. On connect, arcmemory maps a source into three homes: memory (events, outcomes, implicit procedures, project specifics), document search over blob storage (an ontology plus a hybrid index so files are findable without copying them in), and a structured datastore (an ontology so exact queries like "invoice 001" resolve). Three retrieval tools live in arcagent's registry and are invoked by arcrun: memory recall (exists), a NEW hybrid document search (vector + keyword + graph/metadata, fused and reranked), and a structured db-query. The first proof is a triad, one connector per axis: Slack (memory-heavy — implicit procedures, events, decisions), Dropbox (blob doc-search), and a simple SQLite database (datastore query). Eight target sources overall: S3, Slack, OneDrive, Gmail, Calendar, Dropbox, Outlook mail, Notion.

## Audience

Inherits the connector-extensions audience. Josh first — his Slack, his files, his data, working today; if it does not serve him it serves no one. The DGX fleet — each agent reasoning over the systems its role lives in (sales over mail and calendar, coder over Slack and docs, trader over its own record). Buyers of Arc — non-technical people who judge an agent by whether it knows and can use their real data; their path is connect and approve, never an engineering project. Federal operators later — never locked out: every ingest and every retrieval stays signed, identity-scoped, classification-gated, and audited from day one, hardenable without a rewrite.

## Use Cases

Connect Slack — the agent proposes a routing, the operator approves; channel history and ongoing activity become memory (events, decisions, the implicit procedures of how the team works), kept live via webhook; later the agent recalls "how we usually handle X" without being told. Connect Dropbox or S3 — the agent maps the files into a blob ontology and indexes them for hybrid search WITHOUT copying the bodies into memory; in a turn it finds and reads the right contract on demand. Connect a SQLite datastore — the agent maps the schema into an ontology, so "what is invoice 001" resolves as an exact structured query, not a fuzzy match. One source, several homes — Notion pages route to doc-search, its databases to db-query, its activity to memory. Living connections — bounded backfill then incremental sync keeps every home fresh with no re-ingest ritual.

## Desired Outcomes

A connected source stops being inert and becomes usable — routed to the right home and retrievable inside a turn. arcmemory is the routing brain: the decision of memory vs doc-search vs database lives in exactly one place. The agent retrieves like a specialist — analogical memory, hybrid document search, exact database lookup — each with clean, auditable provenance. Don't-copy-what-you-can-point-to becomes real: blobs stay in place, databases stay queried, and memory holds only what memory is for. Connections are living: connect once, it stays fresh. Josh measures success by whether his agents actually know and use his Slack, his files, and his data — not by the architecture.

## Guiding Principles

Route by nature, not convenience: events, outcomes, and procedures go to memory; documents are searched in place; structured records are queried — never ingest a blob or a table into memory. Distinct purpose-built retrieval tools over a magic merger — memory recall, hybrid doc-search, db-query — each auditable on its own; the hybrid (multi-approach + merge) lives INSIDE doc-search, not across homes, and an exact lookup never rides similarity search. Agent proposes, operator approves the mapping: the agent does the heavy lifting, a human confirms once before private data commits to a home. Living by default: bounded backfill + incremental sync; a stale snapshot is a demo, not a coworker. Tools in arcagent, logic in arcmemory, arcrun just calls — no concern crosses a layer. Every ingest and retrieval rides the envelope: signed, identity-scoped, classification-gated (no-read-up), audited — for a Slack message and an S3 object exactly as for a memory card. Degrade, don't crash: no embedder falls back to keyword + graph; a source offline serves what is already indexed. arcmemory holds ontology, index, and pointers — never the bytes of a blob or the rows of a database.

## Constraints

The connectors themselves — auth, transport, and sync plumbing — are the separate 2026-08-04 connector-extensions work; this layer consumes them and must not rebuild them. Sources are heterogeneous: eight auth and sync stories, webhooks where a source offers them and polling otherwise, and backfill that must be windowed and capped so a huge bucket or inbox cannot melt ingest. Blob doc-search must index without copying bodies into arcmemory — chunk, point, and classify remote objects and honor their labels. Database access is a read-only lookup mapped from schema — no unbounded or injected queries (LLM05), no general SQL console. Classification is enforced at the door: a connected object's label gates it in every home, and no-read-up holds on doc-search and db results too. Credentials never touch the filesystem (Arc standing rule) — connectors hold them, this layer never sees a raw secret. Third-party connector code and remote content are untrusted (ASI04/LLM03) and validated at the boundary.

## Scope

**In:** The arcmemory ingestion + routing + ontology layer over connected sources. Agent-proposed, operator-approved mapping into three homes. Memory ingestion of source streams (Slack and peers) through existing capture and consolidation. A blob-storage ontology plus a NEW hybrid document-search retrieval tool (vector + keyword + graph/metadata, fused and reranked) that finds files without copying them. A datastore ontology plus a structured, read-only db-query tool for exact lookup. Bounded backfill + incremental (webhook or poll) sync keeping every home fresh. The first-proof triad end-to-end — Slack (memory), Dropbox (doc-search), a simple SQLite database (datastore) — one connector per axis. Signed, identity-scoped, classification-gated, audited on every ingest and retrieval. The eight target sources as the connector set the layer maps.

**Out:** Building or rebuilding the connectors — auth, transport, webhook plumbing — that is the 2026-08-04 connector-extensions project. The MCP transport work. A unified auto-merging retriever across the three homes. Any human UI beyond the CLI connect and the one approval step. Write-back to sources (sending mail, editing files, updating rows) — that is the connector-extensions' tool surface; this layer reads, ingests, and queries. Sources beyond the eight named. Copying blob bodies or database rows into arcmemory. A general-purpose SQL console — db-query stays a mapped, bounded, read-only lookup.

## Open Questions

How is an ontology represented and stored per home — memory cues and entities exist, but what shape are the blob ontology and the datastore ontology? (/build) How does hybrid doc-search index remote files without holding their bodies — chunk + embed + pointer — and how are remote-object classifications discovered and enforced? How does a DB schema become a safe, bounded, read-only query surface, and what guards against unbounded or injected queries? How is the mapping proposal presented for approval, and re-proposed when a source changes shape over time? Dedup and provenance across homes: the same artifact in Slack and Dropbox — how is it reconciled, and how does a retrieval cite which home answered? How much sync infrastructure (webhook receiver, poll scheduler) is reused from the connector-extensions work versus owned here? Do the three tools need a cheap "where should I look?" hint, or is the agent's tool-selection enough? What are the default backfill window and size caps per source, with operator override?

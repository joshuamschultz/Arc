# Context Management: Arc vs. Agent-Skills-for-Context-Engineering

Source: https://github.com/muratcankoylan/Agent-Skills-for-Context-Engineering

This file records a full audit of the 17 skills in that repo against Arc's real code (not just its docs). 
Each skill was checked by its own agent, reading the skill content and grepping/reading the actual Arc packages before judging fit.

## Summary

Reviewed all 17 context-engineering skills against Arc's real code, not just docs. Below is what already works, what to build next, and what to leave alone.

## Already covered

- **Context assembly** (context-fundamentals): Three-tier system prompt, position-aware placement, observation masking, and threshold-based compaction already match the skill's own best-practice numbers. See `arcagent/core/session_internal/context.py`.
- **Context window management** (context-optimization): Cache-prefix stability, observation masking, threshold compaction, and sub-agent partitioning are all shipped and working together.
- **Agent memory** (memory-systems): Four memory stores, hybrid retrieval, scheduled consolidation, and loud (not silent) failure handling are built in `packages/arcmemory`, and go beyond the skill's own reference examples.

## Worth building (high to low priority)

- **Multi-agent handoffs** (HIGH). Gap: a spawned agent's answer always gets rewritten by the parent before the user sees it, and nothing checks an output before the next task step uses it. Next: add a "pass-through" option to spawn results, plus a verify step before Mission Control tasks unblock. Package: `arcagent`.
- **Long-running task briefs** (HIGH). Gap: spawned agents self-report "done," nothing checks their claim, and there's no way to set an exact success rule or a minimum-effort floor. Next: add success-predicate and effort-floor fields to spawn specs, plus a second fresh-context agent that verifies "done." Package: `arcagent` (orchestration).
- **Conflicting memory facts** (MEDIUM). Gap: when memory returns two facts that disagree, both get loaded with no rule for which one wins. Next: add a conflict check in retrieval with a fixed precedence rule, logged as an audit event. Package: `arcmemory`.
- **Long summaries drifting over time** (MEDIUM). Gap: each compaction re-writes the summary from scratch by LLM, so file and decision lists can quietly vanish over many cycles. Next: merge those fields in code before the LLM call. Package: `arcagent` (session manager).
- **Tool catalog growth** (MEDIUM). Gap: tool categories exist but aren't used, so the list stays flat as it grows, and no naming rule exists yet for MCP tools. Next: group by category now; require full server-qualified names once MCP dispatch ships. Package: `arcagent` (tool registry).
- **Dropped command output** (MEDIUM). Gap: long command output gets cut and the rest is thrown away. Next: save the full output to a scratch file and tell the agent where to find it. Package: `arcrun`.
- **No outcome monitoring** (MEDIUM). Gap: turn outcomes are scored but never rolled into a trend or alert. Next: turn existing outcome labels into a rolling pass-rate with warn/critical audit alerts. Package: `arcagent` (skills module).
- **Judge bias in skill self-editing** (MEDIUM). Gap: the same model writes the edit and grades the edit. Next: let the judge use a separate model, as already done in the memory benchmark. Package: `arcskill`.
- **No reusable safety harness** (MEDIUM). Gap: the lock/edit/log/approve pattern guarding skill self-edits is wired to skills only. Next: pull it into a shared interface in `arcrun` before the next self-driving loop needs it. Package: `arcrun`.
- **Self-edits graded on their own test** (MEDIUM). Gap: a skill's self-edit is judged on the same suite it was tuned against. Next: split the suite into a tuning half and a hidden half; require both to pass. Package: `arcskill`.
- **No cost ceiling on workflows** (MEDIUM). Gap: ArcFlow workflows can ship with no token budget. Next: make a missing budget a warning, or a hard block above personal tier. Package: `arcteam` (workflow).
- **Cold-start sandboxes** (LOW). Gap: every sandboxed run starts from scratch, even on a repeat repo. Next: add a small reuse cache for recent setups. Package: `arcrun`.
- **Plans don't record "why"** (LOW). Gap: plans show what an agent is doing, not which facts justified the goal. Next: add one optional field linking a plan to its motivating facts. Package: `arcagent` (planning).
- **latent-briefing**: this review came back empty (placeholder data, not a real finding). Needs a re-run before anyone acts on it.

## Skip

- Full hosted-agent product features (multiplayer sessions, Slack/Chrome-extension clients). That is a different product than a federal runtime.
- The full BDI/RDF belief-desire-intention model. Arc's existing plan and fact models already cover the real need; a full ontology would bloat the core for no gain.
- Letting agents rewrite `arcrun` or `arcagent` core loop code. Deliberately out of scope. Too big a security risk for a federal harness.

## Full findings, one section per skill

Sorted by priority (high to low), then by status (missing, partial, already-have).

### long-horizon-prompting

**Status:** missing | **Priority:** high

**Core idea:** A discipline for writing the launch prompt of a long-running or many-worker autonomous agent as a "pseudo-formal task brief": define terms precisely, state one exact success predicate, enumerate the near-miss outcomes that do NOT count, require an adversarial fresh-context audit before the run is allowed to return "done," set an effort floor so the agent doesn't quit early, and run parallel workers under a diversity/approach-registry policy so they don't converge on the same wrong answer.

**What Arc already has:** Arc has the runtime scaffolding a brief would plug into but none of the brief discipline itself. `packages/arcrun/src/arcrun/builtins/task_complete.py` is a self-reported completion signal: the agent calls `task_complete(status, summary)` and the loop just terminates on that string — no external check. `packages/arcagent/src/arcagent/orchestration/spawn_handle.py` — `SpawnSpec.task` is a bare `str`; there is no structured success-predicate, non-counting-outcomes, or effort-floor field anywhere in the spawn API. `packages/arcagent/src/arcagent/orchestration/spawn.py` `spawn_many()` fans children out in parallel with no approach registry, no blocked-route bookkeeping, and no diversity policy (grepped for "diversity/approach/registry/verifier/adversarial" in that file — zero hits). `max_turns` (arcrun.toml / arcagent/core/config.py) is a hard budget cap, not an effort floor — it stops runs, it doesn't stop premature give-up. ArcFlow (SPEC-061) stages and Mission Control tasks both terminate the same way: self-reported status, no independent audit-gated acceptance step.

**Gap:** A spawned child (or an ArcFlow stage, or a Mission Control task) declares its own success by writing `status="success"` into `task_complete` — nothing fresh-context or adversarial checks that claim before the parent accepts it and moves on. There is also no way to author a structured task spec (exact success predicate + explicit non-counting near-misses + effort floor) for a long or parallel run; it's one free-text `task` string. For a harness whose stated differentiator is "Arc signs what an agent DOES" and whose Four Pillars already do Identity/Sign/Authorize/Audit on every artifact and tool call, task *outcomes* are the one thing nothing currently verifies — they're taken on the agent's word.

**Recommendation:** In `packages/arcagent/src/arcagent/orchestration/` (spawn concern, stays out of arcrun's loop mechanics and arcllm — concern purity preserved): (1) add optional structured fields to `SpawnSpec` in `spawn_handle.py` — `success_predicate: str | None`, `non_counting_outcomes: list[str] | None`, `effort_floor_turns: int | None` — threaded into the system-prompt builder, no new runtime behavior. (2) Give `spawn_many()` an optional `verify_with: SpawnSpec` on any spec: after the worker's `task_complete` fires, spawn a second fresh-context child (its own derived DID, its own audit trail via existing `spawn.start`/`spawn.complete` events) whose only input is the worker's summary/artifacts plus the success_predicate and non_counting_outcomes, and whose own `task_complete` status becomes the actual acceptance gate for the parent — this makes "done" audit-gated instead of self-reported, reusing existing DID-derivation and audit-emission machinery rather than adding a new subsystem. (3) For diversity, when multiple SpawnSpecs in one `spawn_many` call share an `approach_family` tag, accept only the first that passes verification and emit a `spawn.route_blocked` audit event for the rest — the minimal approach registry the skill calls for. This is directly relevant as ArcFlow and arcteam mature toward multi-hour, multi-worker autonomous runs, which is exactly the scenario this skill targets.

### multi-agent-patterns (orchestrator / peer-to-peer / hierarchical multi-agent architecture)

**Status:** partial | **Priority:** high

**Core idea:** Multi-agent systems should be designed around explicit coordination protocols, not org-chart metaphors. Pick supervisor (centralized delegation), peer-to-peer/swarm (direct handoffs), or hierarchical (layered abstraction) based on coordination need. The two hard failure modes to design against are the "telephone game" (a supervisor paraphrasing a sub-agent's answer loses fidelity) and "error propagation cascades" (one agent's hallucination becomes a downstream agent's accepted fact with no validation checkpoint).

**What Arc already has:** Verified by reading source, not the briefing: (1) Supervisor pattern is real and well-built — packages/arcagent/src/arcagent/orchestration/spawn.py implements spawn()/spawn_many() (child arcrun sub-loops with derived ChildIdentity, RootTokenBudget pooling across parent+children, max_concurrent_spawns semaphore, wallclock timeouts, audit events on spawn.start/spawn.complete). (2) A second, deterministic supervisor variant exists at packages/arcagent/src/arcagent/modules/planning/orchestrator.py (PlanOrchestrator, SPEC-040) — walks a DAG, checkpoints each step, replans on failure via an injected replan_fn, bounded by max_replans. (3) A looser peer-to-peer/async pattern exists in packages/arcteam (team.py TeamStore keyed by DID, mentions.py @handle resolution + attention-flag raising, pull-cursor mailboxes) but it is message-passing between long-lived agents, not the skill's synchronous transfer_to_agent() handoff swarm. (4) GAP CONFIRMED BY CODE: packages/arcagent/src/arcagent/orchestration/spawn_handle.py's SpawnResult has only a `summary: str` field explicitly documented as "Natural-language summary (passed back to the LLM)" — every child result is always re-synthesized by the parent LLM. Grepped the whole tree: zero hits for forward_message, direct_response, consensus, debate, voting, or sycophan* anywhere in arcagent or arcteam (excluding .venv/tests). This matches the project's own memory note (project_orchestration_roadmap.md) that coordinator+verification for multi-agent tasks was explicitly deferred.

**Gap:** Two specific things the skill flags as failure modes are structurally unaddressed: (1) no forward-path exists for a spawned child's output to reach the caller/user verbatim — SpawnResult forces every child result through parent-LLM paraphrase, which is exactly the "telephone game" the skill says causes ~50% quality loss in unmitigated supervisor systems; (2) no validation/verification checkpoint sits between a completed task/spawned child and the downstream consumer of its output — the tasks reliability watcher (dispatch + reliability loops, retry/backoff/dead-letter) checks *liveness* of a task, not *correctness* of its output before dependents proceed, so a hallucinated or wrong result from one agent can silently become an accepted input to the next DAG step.

**Recommendation:** In packages/arcagent, two scoped additions: (a) add an optional `forward_raw: bool` field to SpawnSpec/SpawnResult in orchestration/spawn_handle.py that lets a child mark its output as final-and-verbatim, so the parent's tool-result handling can surface it to the caller without an LLM paraphrase pass — small, typed, no new package, respects concern purity since it's still arcagent-layer bookkeeping, not arcrun loop logic; (b) in modules/tasks (Mission Control), add an opt-in verification step to the reliability watcher: before a completed task's output unblocks dependent DAG nodes, run one bounded verification check (reuse the existing spawn() primitive to spin up a lightweight verifier child with its own DID/audit trail — same pattern already used for task execution, so it stays inside the Four Pillars and doesn't cross into arcrun/arcllm). This directly closes the "error propagation cascade" gotcha for ArcFlow's DAG substrate, which is the highest-consequence place for it in a federal-agentic-harness — a bad output there fans out to every downstream stage/session, not just one chat turn.

### context-degradation (lost-in-middle, poisoning, distraction, confusion, clash)

**Status:** partial | **Priority:** medium

**Core idea:** Context degradation is five distinct, diagnosable failure patterns, not one vague "too much context" problem: lost-in-middle (U-shaped attention curve hurts mid-window info), poisoning (bad claims compound via self-reference, must be truncated not corrected-over), distraction (even one irrelevant document measurably hurts, step-function not linear), confusion (wrong-task constraints bleed in when objectives share a window), and clash (individually-correct but contradictory sources have no priority rule so resolution is unpredictable). Mitigate via four buckets: Write (offload to storage at 70% fill), Select (relevance-filter before loading), Compress (summarize/mask), Isolate (split across sub-agents/sessions).

**What Arc already has:** Verified by reading source, not the briefing: (1) Write/Compress — packages/arcagent/src/arcagent/core/session_internal/context.py: ContextManager.prune_observations() does JetBrains-style observation masking ('[output pruned — N tokens]'), compaction_split() keeps a ~45%-of-window recent tail for SessionManager.compact() (manager.py:254), and transform_context() has a discrete emergency_truncate valve at a hard ceiling — this is a mature, already-documented Write+Compress implementation with an explicit no-per-turn-rewrite design note. (2) Select — packages/arcmemory/src/arcmemory/index/structural.py and surface.py: recall() and search() do top_k relevance retrieval (cosine/fused scoring) with a `degraded` flag, i.e. memory is select-filtered before it ever reaches the prompt. (3) Poisoning — this is Arc's strongest bucket, framed as ASI06/LLM01 rather than "context poisoning" by name: packages/arcagent/src/arcagent/utils/sanitizer.py and modules/policy/policy_engine.py do defense-in-depth neutralization; packages/arcrun/src/arcrun/checkpoint.py refuses a resume with an altered tool set fail-closed as "a poisoned resume"; packages/arcmemory/src/arcmemory/index/rebuild.py deterministically wipes and re-derives a corrupted/poisoned index rather than layering corrections. (4) Isolate — module_bus event-driven modules, arcteam per-agent isolated subdirectories (arcteam/files.py), and ArcFlow's per-stage sessions all split context by task. (5) Lost-in-middle — ContextManager.assemble_system_prompt() tiers sections into session/run/turn with a fixed head + alphabetical + fixed tail ordering, which is a positional-placement strategy even though it isn't labeled "attention U-curve."

**Gap:** Context Clash has no dedicated code anywhere in the repo. Grepped packages/arcmemory and packages/arcagent for precedence/contradict/conflict — zero matches outside tests. When arcmemory's top_k retrieval returns multiple recalls, or multiple tool outputs / skill or blueprint versions disagree, Arc has no mechanism to detect the contradiction, mark which source takes precedence, or annotate it before the content reaches the prompt — it silently includes both and lets the model resolve unpredictably, exactly the failure mode the skill warns about. This is distinct from poisoning (both sources are individually correct, just mutually contradictory) and distinct from Select (both are relevant, just conflicting) — none of Arc's existing four-bucket coverage touches it. There's also no context-health/degradation monitoring surface (no attention-distribution or fill-vs-accuracy correlation tracking) beyond the raw token_ratio() used only to trigger compaction.

**Recommendation:** In packages/arcmemory, add a conflict-detection pass in the retrieval path (structural.py's recall()/trigger_match() or a small new conflict.py module) that runs when top_k returns multiple recalls touching the same entity/topic with divergent content: emit a structured conflict record (source, claim, timestamp/confidence, precedence rule — e.g. most-recent-consolidation-wins) instead of silently threading both into context.md. Emit it through arctrust.audit so a resolved conflict is itself an auditable event (NIST SI-10 information-integrity relevance), and keep the precedence rule deterministic and LLM-uninvolved per the existing 'LLM-confirmed dedup, never auto-merge' pattern already used for entity dedup. Do not touch arcagent's ContextManager for this — clash is a memory-provenance problem, not a prompt-assembly problem, so it belongs in the arcmemory package to respect concern purity.

### context-compression

**Status:** partial | **Priority:** medium

**Core idea:** For long-running agent sessions, compress conversation history to save tokens, but optimize for tokens-per-task (total cost including re-fetching) not tokens-per-request. Use structured summaries with mandatory sections (files modified, decisions, next steps) as a checklist that prevents silent information loss, trigger compaction at a fixed 70-80% context threshold, and merge/anchor new summaries onto old ones incrementally rather than regenerating from scratch every cycle to avoid compounding drift across repeated compactions.

**What Arc already has:** packages/arcagent/src/arcagent/core/session_internal/manager.py: SessionManager.compact() is the sole compactor (single discrete path, matches memory note project_compaction_single_path). It does exactly what the skill recommends structurally: (1) fixed-threshold trigger — packages/arcagent/src/arcagent/core/config.py ContextConfig has prune_threshold=0.70 and compact_threshold=0.85, matching the skill's 70-80% guidance almost exactly; (2) deep token-based split keeping a recent tail (~45% of max_tokens) via context.py compaction_split(); (3) structured, schema-forced summarization via packages/arcagent/src/arcagent/context/summary_template.md, which has explicit mandatory sections (goal, constraints, progress, key_facts, files_modified, decisions, rejected_approaches, open_questions, next_step) with goal/constraints copied verbatim — a direct match to the skill's "Structure Summaries with Mandatory Sections" and the "protect early-turn constraints" gotcha; (4) observation masking of stale tool outputs via context.py prune_observations(), protecting the most recent ~20% of tokens; (5) the LLM-produced summary is sanitized before it re-enters the message baseline (ASI-06 injection-laundering guard), addressing the skill's "compressed summaries hallucinate facts" gotcha, at least for injected content; (6) an audit event (context.compaction) fires on every compaction, satisfying Arc's Four Pillars.

**Gap:** Each compaction cycle calls the LLM to regenerate the structured summary fresh from (previous summary text + new messages) rather than deterministically merging/deduping the structured fields (e.g. files_modified by path, decisions list) the way the skill's "Anchored Iterative Summarization" recommends. Over many compaction cycles on a long-running agent (Arc's stated target: thousands of agents, continuous scheduler/task/ArcFlow loops that can run for weeks), this is exactly the "aggressive ratios compound across cycles" gotcha — file paths and decisions can silently drop or get paraphrased away because preservation is left to the summarizer model's judgment each round instead of code. There is also no probe-based evaluation of compaction quality (nothing checks that a compacted session still correctly answers "what files did we touch") and no per-cycle provenance tag on summary fields, so drift would be invisible until an agent visibly "forgets" a file it modified several compactions ago.

**Recommendation:** In packages/arcagent/src/arcagent/core/session_internal/manager.py, when the message being summarized (to_summarize) already contains a prior compaction_summary entry, parse its structured fields (a small deterministic step, not an LLM call) and programmatically merge files_modified (dedup by path, keep newest description) and decisions (append, dedup by decision key) into the new summary before the LLM call, instead of relying solely on the summarizer to carry them forward from raw text. This is a small, in-place change to the existing single compactor — no new path, no new package, no legacy shim — and directly closes the "agent forgets what files it modified" failure mode the skill calls out as the costliest compression bug, which matters specifically because Arc's mission is long-running fleets of agents where a session can live for weeks, not a one-off debugging chat.

### tool-design

**Status:** partial | **Priority:** medium

**Core idea:** Design every agent tool as an explicit contract the agent can infer from the description alone: state what it does, when to use it, its input schema, and what it returns. Consolidate overlapping tools into fewer comprehensive ones, namespace tools as the catalog grows, and make error messages actionable (what went wrong + how to fix it) so the agent can self-correct instead of stalling.

**What Arc already has:** Verified in packages/arcagent/src/arcagent/core/tool_registry.py and tools/_transport.py: RegisteredTool already carries description, when_to_use, example, and category fields; ToolRegistry.format_for_prompt() injects an XML &lt;available-tools&gt; catalog with description/when-to-use/example per tool — this is exactly the skill's "tool description as prompt" pattern, already built. Error design is also strong: tool_registry.py's _validate_tool_args raises ToolError(code="TOOL_INVALID_ARGS", message=f"missing required argument: {field_name}") and similar for unknown args (actionable, names the exact field). arcrun/src/arcrun/executor.py converts every failure mode (denied, not-found, invalid params, timeout, exception) into a tool_result string like "Error: invalid params — {msg}" fed back into the ReAct loop rather than crashing the run, so the agent literally sees and can retry on the error — matches the skill's "error message design for agent recovery" almost exactly. Naming is fairly consistent verb/noun (bash, read, write, edit, grep, find, ls, create_skill, update_tool).

**Gap:** The consolidation/namespacing half of the skill is unwired. RegisteredTool.category exists as a field and is rendered into the XML catalog, but grep across packages/arcagent/src shows zero of the actual builtin capability tools (bash, read, write, edit, grep, find, ls, create_skill, create_tool, reload, store_secret, update_skill, update_tool) set category= — so today's growing flat catalog (13 builtins plus per-module tools from tasks/workflow/memory/scheduler) has no domain grouping in what the agent sees, exactly the flat-list degradation the skill warns about. There is also no tool-overlap audit (no test/lint that fails when two tools share an activation scenario) and no MCP naming enforcement — confirmed MCP transport has zero dispatch usage (ToolTransport.MCP defined but never used to route a call), matching the briefing's "MCP unfinished" note. That means when MCP dispatch is eventually built, nothing in tool_registry.py today would stop two MCP servers' tools from colliding under the same bare name, which is precisely the failure mode the skill's "MCP Tool Naming Requirements" section calls out (must be ServerName:tool_name, fully qualified).

**Recommendation:** In packages/arcagent/src/arcagent/core/tool_registry.py: (1) start populating RegisteredTool.category on the builtin capability tools (packages/arcagent/src/arcagent/builtins/capabilities/*.py) and module-registered tools, then group by category in format_for_prompt()'s XML output so the catalog is namespaced instead of flat as it grows; (2) when MCP dispatch is implemented (the decided-but-unfinished extensibility spine), enforce fully-qualified ServerName:tool_name in ToolRegistry.register() for any tool with transport == ToolTransport.MCP — reject or auto-prefix bare names — so multi-server collisions fail at registration time, not at agent-selection time. This is a small, scoped addition to the existing register()/format_for_prompt() methods, not a new subsystem, and it closes the gap before MCP dispatch ships rather than after.

### filesystem-context

**Status:** partial | **Priority:** medium

**Core idea:** Use the filesystem as an overflow layer for agent context: redirect large tool outputs to files and return compact summaries/references instead of stuffing them in the context window (tool-output offloading), keep durable structured plans on disk that get re-read each turn (plan persistence), and let sub-agents hand off findings via per-agent workspace files instead of lossy message chains.

**What Arc already has:** Arc already has strong filesystem-context primitives, just not the offload-on-overflow pattern. Verified by reading code: (1) every agent has a workspace-rooted file surface — packages/arcagent/src/arcagent/builtins/capabilities/{read,write,edit,grep,find}.py — read.py supports offset/limit seeking and a 10MB size cap, matching the skill's 'targeted retrieval' and 'check file size before reading' guidance almost exactly. (2) packages/arcagent/src/arcagent/modules/workpad/_runtime.py rewrites the agent's own context.md as an 'open loops' cockpit every N turns via direct filesystem I/O (ADR-029) — this is Pattern 6 (self-modification/learning) already shipped, and per session_internal/context.py it's re-read every turn as the run-stable prompt segment (Pattern 2, recitation). (3) packages/arcagent/src/arcagent/modules/planning/{store.py,models.py,decomposer.py,executor.py,orchestrator.py} is a structured, persisted plan/task DAG store re-read across turns — a stronger, DB-backed version of the skill's YAML plan-persistence pattern. (4) Tool output IS size-capped: packages/arcrun/src/arcrun/backends/base.py (TRUNCATION_MARKER, max_stdout_bytes) and builtins/execute.py / contained_execute.py (max_output_bytes=65536) hard-truncate stdout/stderr.

**Gap:** The truncation path in arcrun DROPS the overflow instead of offloading it. backends/base.py's _ThreadedProcessHandle.start() does `truncated = result[:self._max_stdout_bytes]`, writes only that slice, and discards the rest — same pattern in execute.py/contained_execute.py (`result.stdout[:max_output_bytes]`). This is the skill's exact 'Missing context' failure mode: a long test run, build log, or verbose CLI command beyond ~64KB is permanently lost, not written anywhere for later grep/read retrieval. There is no 'write full output to scratch file, return summary + path' behavior (Pattern 1) and no persisted, greppable terminal/log store (Pattern 5) — the read/write/edit/grep tools exist but nothing in the execute path uses them to persist what it truncates.

**Recommendation:** In packages/arcrun/src/arcrun/backends/base.py and builtins/execute.py + contained_execute.py: when captured stdout/stderr exceeds max_stdout_bytes/max_output_bytes, write the FULL untruncated bytes via plain filesystem I/O (not through the LLM write tool — this is backend code, not an LLM tool call, so ADR-029's spirit is naturally satisfied) to a scratch file under the already-resolved workspace-scoped working directory, e.g. `<workspace>/scratch/exec/<timestamp>-<tool_call_id>.log`, and change the tool_result content returned to the model from silent truncation to something like `Error/Notice: output truncated at N bytes; full output written to scratch/exec/....log — use read(offset,limit) or grep to inspect it`. Keep it arcrun-only (loop/backend concern, not arcagent or arcllm) and keep it a one-line addition to the existing truncation branch — no new module, no config flag beyond the existing max_output_bytes.

### evaluation

**Status:** partial | **Priority:** medium

**Core idea:** A framework for judging agent systems on outcomes, not steps: deterministic checks run first, then multi-dimensional rubrics (not one score), stratified regression test sets (at least 50 cases, by difficulty), and continuous production monitoring with pass-rate alert thresholds (warn 0.85, critical 0.70) that gate deploys and catch drift over time.

**What Arc already has:** Arc already builds this pattern, but only for one narrow use case: skill self-mutation acceptance in arcskill.improver (SPEC-054). packages/arcskill/src/arcskill/improver/evalgate.py is a deterministic golden-task gate with a strict-improvement rule (>=1 previously-failing case now passes, zero regressions) and a fail-closed no-suite policy per tier. packages/arcskill/src/arcskill/improver/evaluator.py is a genuine multi-dimensional LLM-as-judge (one call per rubric dimension per trace, 1-5 scale, per-dimension scores stored not averaged away). packages/arcskill/src/arcskill/improver/suitegen.py runs an anti-tautology + negative-control-mutation adoption cascade before any generated case is trusted as a golden anchor. packages/arcagent/src/arcagent/modules/skills/outcome.py is a turn-end implicit-outcome classifier (lexicon pre-filter -> LLM label) that feeds the trace store's outcome_source field. improver.py has a lazy "suite-less skills get bootstrapped, most-used-first" backstop (REQ-107), so the wiring is real, not vestigial.

**Gap:** All of this machinery only decides whether to accept a mutated skill. Nothing rolls the turn-end outcome labels up over time into a monitored pass-rate metric, nothing compares against a baseline before/after an arcagent or arcrun code change, and there is zero equivalent regression harness for the parts of Arc that most need one for the federal mission: ArcFlow workflow runs, task-dispatch/reliability outcomes, or arcteam coordination quality. Verified directly: 0 skills in the repo currently have an evals/ directory, and outcome labels are written to the per-skill trace store but nothing consumes them as a trend, threshold, or alert -- the 0.85 warn / 0.70 critical pattern this skill recommends does not exist anywhere in Arc.

**Recommendation:** In arcagent/modules/skills/ (not arcskill -- keeps arcagent orchestrating and arcskill's improver untouched, respecting concern purity), add a small rollup that reads the outcome_source labels the turn-end OutcomeClassifier is already producing, computes a rolling per-agent pass rate over a fixed window, and emits it through arctrust.audit.emit (the existing Audit pillar sink, so it reaches arcui's UIBridgeSink for free) whenever the rate crosses 0.85 (warn) or 0.70 (critical). This reuses data Arc is already generating instead of building a new judge, needs no new package, and turns a currently write-only trace log into the production quality gate this concept requires -- directly relevant to ASI10 (rogue-agent/anomaly detection) and ASI06 (context/memory poisoning from bad self-mutation) in the project's own threat table.

### advanced-evaluation (LLM-as-Judge: direct scoring, pairwise comparison, rubric generation, bias mitigation)

**Status:** partial | **Priority:** medium

**Core idea:** A family of techniques for using an LLM to grade another LLM's output: direct scoring (1 response, rubric, 1-5 scale) for objective criteria, pairwise comparison with position-swap for subjective preference, rubric generation with level descriptions and edge cases, and bias mitigation (position, length, self-enhancement, verbosity, authority bias) plus confidence calibration.

**What Arc already has:** Two real, tested implementations exist. (1) packages/arcskill/src/arcskill/improver/evaluator.py — SkillEvaluator is a textbook Direct Scoring judge: per-dimension, per-trace, evidence-first checklist (YES/NO) before a 1-5 score (config.eval_scale), rubric loaded via arcskill.context.load_rubric with an "anti_inflation" clause per dimension, JSON output parsed with a safe low-score fallback. This is a same-package, same-seam change — no new dependency edges, respects concern purity — and directly closes the self-enhancement-bias gap the skill calls out as a top mitigation ("use different models for generation and evaluation"). ### harness-engineering

**Core idea:** Defines the control system around a long-running autonomous agent loop: separate surfaces (locked eval, editable artifact, append-only log, human-controlled actions), a tight feedback loop with cheap rollback, durable state that survives context loss, novelty/pruning gates so the agent doesn't stack complexity or relitigate rejected ideas, and an explicit boundary between "agent can prepare" vs "human must approve" (e.g. PR-not-merge).

**Recommendation:** In arcrun (the loop-execution layer, per concern-purity), define a small typed Protocol — e.g. BoundedLoop with locked_evaluate(), append_log(), request_approval() — capturing the four-surface boundary generically with zero skill-specific or LLM-provider logic inside it. ### self-improvement-loops

**Status:** partial | **Priority:** medium

**Core idea:** Treats the harness/scaffold itself as the thing being optimized: an agent mines its own failure traces and proposes bounded self-edits to its own prompts, context, workflow, or code, gated by empirical acceptance (a held-in AND held-out split that must not regress) rather than the proposer's rationale, with the evaluator kept outside the loop's reach and diversity preserved via an archive so the loop doesn't collapse onto one brittle candidate.

**What Arc already has:** packages/arcskill/src/arcskill/improver/ is a mature, live implementation of most of this skill's mechanics, but scoped only to individual skills (rung 1/2/5 of the ladder), not the harness/loop/workflow-graph itself. Concretely: improver.py wires observe/on_turn_end/maybe_improve/review_lifecycle signals, runs optimization in a caught background task (NFR-005) so a failing self-edit never touches the agent loop -- this IS the 'outside-the-loop invariant' for blast-radius. evalgate.py implements a deterministic golden-task gate that accepts a candidate only on strict improvement (>=1 previously-failing case now passes, zero regressions) -- the skill's 'empirical acceptance, never rationale' principle, plus provenance tracking (machine- vs human-authored eval cases via a @generated marker cross-checked against a harness-written manifest, so a model can't self-assert human authorship of its own test cases -- this is a stronger anti-gaming control than the source skill even describes). improver.py._record_rejection / _compose_failures feeds a bounded buffer of prior REJECTED patches back to the mutator as negative feedback (explicitly named 'the SkillOpt rejected-edit buffer... the credited convergence lever' in the docstring) -- matches the skill's 'log rejected candidates with evidence so the proposer stops rediscovering them.' candidate_store.py persists per-skill candidate lineage + manifest + append-only audit log with rollback(). guardrails.py + ChangeBound (codepatch/config.py) implement a cosine-decaying per-attempt edit budget across the improve-attempts-before-retire window -- matches 'bounded proposal, minimal, touch one surface.' lifecycle.py implements retire/revive as audited state transitions (stagnation/inactivity handling). pareto.py implements a per-skill multi-objective Pareto frontier over candidate score vectors (GEPA/ACE-style prose evolution, not monolithic rewrite). Tier-gated operator-approval ladder (federal approves every mutation, enterprise only code, personal auto+audit-warn) is fail-closed when unwired. sandbox_runner.py (HubEvalRunner) sandboxes untrusted eval execution. SPEC-044 and SPEC-054 (skill-improver eval bootstrap) both show status COMPLETE.

**Gap:** Two real gaps, both scoped to arcskill/improver, not the whole harness. (1) No held-in/held-out split: EvalGate.decide() runs the SAME golden suite before and after the candidate and calls that 'strict improvement' -- there is no second, held-out split that the mutator/SuiteGenerator never sees, so a self-edit (or an LLM-authored eval case) could in principle special-case the one suite it is judged against. The published two-split rule this skill cites is specifically designed to catch that failure mode; Arc's provenance/manifest check mitigates model-forged human-authorship but doesn't substitute for held-out generalization evidence. (2) Scope ceiling: this entire self-improvement machinery only ever touches SKILL.md prose and skill-local scripts (packages/arcskill). Nothing in Arc applies rungs 4-6 of the skill's ladder -- there is no self-edit loop over arcrun's loop code, arcagent's orchestrator code, or ArcFlow's workflow.toml DAGs; ArcFlow is explicitly a static signed graph and arcrun's 'strategies' (dynamic graph emergent from tool calls) are designed-not-built per project memory. That's a deliberate and correct boundary for a federal harness (self-modifying core loop code would be a much bigger ASI04/ASI05 surface), so it should stay out of scope rather than be treated as a gap to close.

**Recommendation:** In packages/arcskill/src/arcskill/improver/evalgate.py, split load_suite()'s cases into a held-in set (used by SkillEvaluator/SuiteGenerator during proposal and shown in the rejected-edit buffer feedback) and a held-out set (generated the same way but never surfaced to the mutator/reflector prompts), then change EvalGate.decide() to require zero regression on BOTH splits and strict improvement on at least one before GateDecision.accepted=True -- mirroring the source skill's Example 1 accept() function. This is a config.py (split ratio, min per-split case count) + evalgate.py change only; it stays inside arcskill, doesn't touch arcrun/arcagent/arcllm, and doesn't require a new package or shim.

### hosted-agents

**Status:** partial | **Priority:** low

(2) Self-spawning agents — packages/arcagent/src/arcagent/orchestration/spawn.py + spawn_handle.py already implement exactly what the skill asks for: spawn()/spawn_many() launch child runs with derived child DIDs, wall-clock timeouts, max_concurrent_spawns, RootTokenBudget enforcement, and spawn.start/spawn.complete audit events — arguably more federal-grade than the skill's own description (it has no audit/DID concept at all). **Gap:** What Arc does NOT have is the specific "hosted background coding agent" product lifecycle this skill is really about: no image-registry pattern (pre-cloning the repo + installing deps + warming caches on a rebuild cadence), no warm pool of pre-spun sandboxes, no predictive warm-up on user typing, and no filesystem snapshot/restore of a sandbox's working state for a fast follow-up turn. This is additive, respects the existing fail-closed/deny-by-default guest posture (no new trust boundary — the pool just skips redundant setup work inside the same signed backend), and directly reduces cost/latency for ArcFlow and task-dispatched coding work that repeatedly hits the same repo. Do not build the multiplayer/Slack-virality/Chrome-extension pieces — those target a different product (a coding-agent SaaS) and don't serve Arc's federal-harness mission.

### bdi-mental-states

**Status:** partial | **Priority:** low

**Core idea:** Formal cognitive modeling for agents: incoming facts become typed Beliefs, Beliefs motivate Desires, Desires get committed to Intentions that specify Plans of ordered Tasks. Every mental state carries a Justification (provenance) and a temporal validity interval, all serialized as RDF/Turtle so it's SPARQL-queryable and explainable ("why did the agent believe/want/do this?"). It's a two-phase pipeline (Triples-to-Beliefs-to-Triples) meant for cross-agent semantic interoperability.

**What Arc already has:** Arc already has the practical skeleton of the Intention/Plan/Task half: `packages/arcagent/src/arcagent/modules/planning/` (SPEC-040/021) decomposes a Goal into a `Plan` (DAG of `PlanStep`, `depends_on`, `status: PENDING/READY/RUNNING/SUCCEEDED/FAILED/SKIPPED`) via `decomposer.py` (ReWOO-style one-shot decompose + Reflexion-lite replan on failure), executed through a `StepExecutor` seam and exposed as tools (`plan_create`, `plan_status`, `plan_replan`, `plan_abandon`). Separately, `packages/arcmemory/src/arcmemory/types.py` has a `Fact` model (predicate/value/confidence/date + `was_value`/`was_confidence` contradiction trail) and `Entity` — a belief-like revision-tracked fact store, but not named or wired as "belief." Grep for `\bbelief\b|\bdesire\b|\bintention\b` across `packages/**/*.py` (excluding tests) turns up zero real hits — only incidental uses of the word "desired." No RDF/ontology, no `Justification` object, no `motivates`/`isMotivatedBy` linkage, no SPARQL layer anywhere in the repo.

The full RDF/Turtle/SPARQL ontology apparatus from the skill is not present and, per Arc's own simplicity principle (core <3,500 LOC, no abstraction before three real instances), would be over-engineering for a system whose existing typed Plan/Fact models already cover the operational need.

### context-fundamentals

**Status:** already-have | **Priority:** low

**Core idea:** Context is the model's whole visible state (system prompt, tools, retrieved docs, message history, tool outputs) and it is a finite, saturating attention budget, not a storage bin — quality (signal density, position, progressive disclosure) beats raw quantity, and the middle of a long prompt gets less attention than the edges.

**What Arc already has:** packages/arcagent/src/arcagent/core/session_internal/context.py implements this concept more precisely than the skill's own guidance: (1) three-tier system-prompt assembly by change rate — session-stable (identity, capabilities), run-stable (context.md), per-turn (recall/planning/teams) kept OUT of the system prompt so the provider cache prefix stays byte-stable; (2) explicit position-aware placement (_SESSION_HEAD, _RUN_TAIL constants); (3) XML tag boundaries with a _defang() fixed-point stripper defending against prompt-injection forgery of section boundaries (LLM01); (4) observation masking via prune_observations() replacing stale tool output with '[output pruned — N tokens]' placeholders; (5) discrete, threshold-triggered compaction in SessionManager.compact() (manager.py:254) with compaction_split() doing a token-budgeted deep split (~45% keep-budget) plus an emergency_truncate() last-resort valve — matching the skill's 'compaction triggers at 70-80% utilization' guideline almost exactly; (6) transform_context is append-only per turn, exactly the skill's 'cyclically refine history, don't rewrite per turn' pattern. The workpad module's context.md self-rewrite is the progressive-disclosure/just-in-time-retrieval piece for agent state.

**Gap:** The one anatomy component the skill calls out that Arc does not measure or enforce is tool-definition token bloat. tool_registry.py (core) renders tool descriptions/schemas into the prompt but has no check on serialized JSON/XML size, no consolidation gate, and no audit signal when the tool set for an agent crosses a token budget — the skill's own top gotcha ('tool schemas inflate 2-3x after JSON serialization... audit serialized tool token counts, not source-code line counts') has no analog here.

**Recommendation:** In packages/arcagent/src/arcagent/core/tool_registry.py, add a build-time token-budget check on the assembled tool-description block (reuse ContextManager.estimate_tokens): compute the serialized size of the agent's active tool set, log a structured warning (and emit an arctrust audit event, not just a log line) when it crosses a configurable threshold in config.py's ContextConfig, so operators see tool-schema bloat before it silently eats the attention budget at scale (thousands of agents, cold-start/memory budgets already tracked elsewhere). Keep it a warn/audit signal, not a hard block — this is context hygiene, not a security gate.

### context-optimization

**Status:** already-have | **Priority:** low

**Core idea:** Extend effective context-window capacity via four layered techniques in priority order: KV-cache/prefix stability, observation masking (replace stale tool outputs with retrievable references), threshold-triggered lossy compaction, and context partitioning across sub-agents — each with target metrics (e.g. mask 60-80% of stale observations, compact at 70-80% utilization, never mask active-debug errors, never let dynamic content break the prefix).

**What Arc already has:** packages/arcagent/src/arcagent/core/session_internal/context.py: ContextManager.transform_context is append-only specifically to keep the provider cache prefix byte-stable, with a tiered system-prompt design (session-stable / run-stable / per-turn) documented in the module docstring: "one volatile byte in front of the history re-bills the entire history every turn." ContextManager.prune_observations (line 405) is literal observation masking: replaces stale tool outputs with "[output pruned — N tokens]" placeholders while protecting a configurable recent-token window, citing "Observation masking (JetBrains Research)" by name. packages/arcagent/src/arcagent/core/session_internal/manager.py: SessionManager.compact (line 254) is threshold-triggered — agent_dispatch.py's maybe_compact checks session.context_ratio() >= config.context.compact_threshold — does a deep token-based split (~45% recent tail kept), produces a structured LLM summary (schema not prose), applies prune_observations to the kept window, persists the result, and emits an audit event. packages/arcllm/src/arcllm/adapters/anthropic.py has real Anthropic cache_control markers (lines 132-216), genuine KV-cache prefix reuse. arcteam mailboxes + ArcFlow stage-session isolation function as the skill's "context partitioning across sub-agents."

**Gap:** Arc has only a single global context_ratio() threshold (compact_threshold) that fires one compaction action for the whole window. It does not track or budget individual categories (tool outputs, message history, retrieved docs, reserved buffer) separately the way the skill's Budget Management section recommends, so it cannot react differently when, say, tool outputs alone blow the budget versus when history does.

**Recommendation:** In packages/arcagent/src/arcagent/core/config.py's ContextConfig, add optional per-category budget fields (e.g. tool_output_budget_ratio, history_budget_ratio, default None so this stays opt-in and doesn't grow core LOC). Have session_internal/context.py's token-estimation pass report per-category usage alongside the existing context_ratio(), and feed that into agent_dispatch.py's maybe_compact so it can choose a targeted action (mask only tool outputs when that category is over budget vs. a full compact when the total crosses threshold) instead of always doing one full compaction. Keep this inside arcagent core/session_internal — it's context-management logic, not agent-state I/O, so it doesn't touch the ADR-029 workspace-write boundary, and it must not leak into arcrun or arcllm (concern purity).

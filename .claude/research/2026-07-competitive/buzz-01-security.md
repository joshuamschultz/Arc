## (b) Verdict on Arc's 4 moat claims

1. **Tamper-evident hash-chained audit** — **SURVIVES, materially**. Buzz has a hash chain but explicitly disclaims tamper-*resistance* (SECURITY.md, quoted above) — no per-entry signature, no external witness. Arc's Ed25519-per-record signing + independently-custodied `WitnessAnchor` closes exactly the gap Buzz admits it has left open. Decided by: `audit.py:279-305` (sign) vs `hash.rs:42-73` (hash only) + Buzz's own SECURITY.md sentence.
2. **Signed inter-agent messages** — **PARTIALLY CONTESTED**. Buzz's NIP-98/NIP-42 do sign every request/connection at the transport/protocol layer — genuinely comparable to "authenticates the act." But this is relay-message signing, not the tool-call-level signed dispatch Arc's `PolicyPipeline`/`IdentityLayer` implies; and I found no evidence of per-tool-call signing inside `buzz-agent` itself. Decided by: `nip98.rs:55-131` vs absence of equivalent in `buzz-agent/src/auth.rs`.
3. **Signed extension supply chain** — **SURVIVES**. Arc has working Sigstore/cosign verification for skills (`verify.py`, `installer.py:333`). Buzz has `cargo-deny` (dependency hygiene, with several advisories waived) and git-commit signing, but no signing/verification of agents, workflows, or MCP servers as loaded artifacts.
4. **Cryptographic agent identity** — **CONTESTED, non-trivially**. Both are real Ed25519-class/Schnorr identity systems. Buzz's identity is per-account (Nostr keypair, OS-keyring-stored) rather than obviously per-agent-*instance* with derived short-lived children (Arc's `derive_child_identity`, HKDF, monotone clearance) — but I did not find the negative evidence conclusively (buzz-agent key-minting code wasn't in the files read). Score this a draw pending more code.

## (c) What Buzz does better — adopt

- **Real formal verification** (TLA+ TLC-checked to completion + Tamarin/Dolev-Yao model) of its multi-tenant isolation and auth protocol. Arc has zero formal-methods artifacts. This is a legitimate, checkable claim Buzz can point to that Arc cannot.
- **Honest security disclosure**: Buzz's SECURITY.md states its own audit weakness in plain language. Arc should hold itself to the same standard in comparable docs.
- **SSRF-blocklist + size-capped webhook/eval sandboxing** for workflow automation — narrow but concrete.

## (d) What Arc genuinely still does better

- Signed, tamper-*resistant* audit with independent witness anchor (not just chained hash).
- A real multi-layer, classification-aware, tier-scoped policy engine vs. Buzz's single membership gate.
- A working signed supply chain (Sigstore/cosign) for loaded extensions.
- Explicit compliance target (FedRAMP/NIST) architecture, not just a compliance *label* on a feature.

## (e) Bottom line

Arc's moat is narrower than the original roadmap claimed but not gone. Buzz genuinely has signed-per-request identity (NIP-98/42) and a rigorous formal-methods artifact Arc lacks entirely — say so plainly, don't spin it away. But on the two claims that matter most under an adversarial/insider threat model — audit tamper-*resistance* and authorization granularity — Buzz's own documentation concedes the gap Arc closes (keyless chain vs. signed+witnessed chain; membership-only gate vs. layered policy engine). The honest differentiator to lead with going forward is **operator-adversarial hardening**: Arc assumes the person with DB/root access might be the threat (external witness, classification-aware policy, fail-closed federal tier) and builds for that; Buzz's threat model, as written, does not yet reach that bar. That is a real, defensible, narrower moat — not "uncontested on all four," but not defeated either.

## Addendum: Per-Action Signing Resolution

Traced the full path: LLM decides to call a tool → `RunCtx::execute_calls` (`buzz-agent/src/agent.rs:295-348`) → `invoke_tool_inner` (`agent.rs:501-543`) → `McpRegistry::call` (`buzz-agent/src/mcp.rs:485-553`) → `do_call` (`mcp.rs:556` onward), which builds a raw `CallToolRequest` and sends it over the `rmcp` MCP peer connection (`mcp.rs:580-588`). **No signature, no cryptographic attestation, and no audit-chain emission appear anywhere in this path.** The only gates present are process-lifecycle bookkeeping (`ClientState::Healthy`/`Dead`, `killpg` on timeout, restart backoff) and mechanical caps (`MAX_TOOL_CALLS_PER_TURN`, unknown-tool-name rejection, hook-tool invisibility). A tool call never touches `buzz-audit` — I confirmed no reference to the audit crate, an event id, or a Nostr signature anywhere in `agent.rs` or `mcp.rs`.

`buzz-persona/src/persona.rs` (full file, 645 lines) confirms a **persona holds no key material at all** — `PersonaConfig` is a pure YAML-frontmatter+markdown parser (name, display_name, skills, `mcp_servers`, triggers, model string). No `Keys`, no `nsec`, no signing anywhere in the type. The only Nostr key-generation call found in the agent-facing crates is `buzz-pairing-cli/src/main.rs:589` (`Keys::generate()`), and that is explicitly a **test-key fallback for the device-pairing CLI**, not per-agent-instance minting. Combined with `SECURITY.md`'s keyring section (keys stored per human/managed-agent **account** in the OS keyring, or via `BUZZ_PRIVATE_KEY` env for "harnessed agents and CI"), the identity model reads as **per-account, not per-instance**: one persistent Nostr keypair per agent *account*, reused across every session and every tool call that agent ever makes — there is no Arc-style ephemeral child identity derived per spawn.

**Resolved claim 2**: Buzz signs what an agent SAYS (every relay-bound HTTP request via NIP-98, every WebSocket session via NIP-42 — real, per-request, verified in `nip98.rs`), not what an agent DOES. Tool invocation over MCP is entirely unsigned and unaudited at the point of dispatch. Arc signs the tool call itself (via `PolicyPipeline`/`IdentityLayer`, per `policy.py`) and gates it *before* dispatch. Recommend dropping "partially contested" for claim 2 — **claim 2 SURVIVES**: Buzz's signing boundary is one layer higher up the stack than Arc's, and the layer it skips (the tool call) is the one an OWASP ASI02/LLM06-style "excessive agency" attack actually exploits.

**Resolved claim 4**: leaning **SURVIVES for Arc**, not a draw. Buzz's identity is a static per-account Nostr keypair with no derivation, no TTL, no clearance-narrowing; Arc's `derive_child_identity` (HKDF-SHA256, per-spawn nonce, monotone-non-increasing clearance, TTL-bound) is a materially different and stronger primitive for containing a compromised or misbehaving spawned agent. Buzz has nothing structurally comparable in the crates read.

**Per-tool-call authorization gate**: confirmed **none exists** in `buzz-agent`. The only "deny" surfaces in the tool-call path are technical (unknown tool name, dead MCP server, timeout) — never policy-based (no classification check, no per-tool allow/deny rule, no caller-identity check). Authorization is genuinely channel-membership-only, and even that gate lives at the relay (`buzz-auth/access.rs`), not in the agent's own tool-dispatch loop — so a Buzz agent's *local* tool use (shell, file read, MCP servers in its persona config) has **no runtime authorization gate at all**, only whatever the persona's static `mcp_servers` list happens to expose. This directly confirms SECURITY.md's "channel membership is the only access control mechanism" and extends it: that gate doesn't even reach tool calls, only relay reads/writes.

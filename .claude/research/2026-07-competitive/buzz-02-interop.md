## (b) How far ahead Buzz is

Buzz ships a **complete, tested, bidirectional interop stack** across three independent layers — MCP (client + server), ACP (agent + host), and Nostr (relay + git-signing + SDK) — with regression tests locking down cancellation, process-group kill, and restart/backoff behavior (`buzz-agent/src/mcp.rs:1005-1139`). Arc has **zero working code** on any of these three layers; ADR-018 explicitly and deliberately excluded MCP client, ACP adapter, and migration tooling from scope (`docs/architecture/decisions/ADR-018-no-mcp-no-migration-no-acp.md`). Concretely: Buzz can call any of thousands of existing MCP servers, be called by any ACP editor (Zed, JetBrains) or CLI, drive Codex/Claude Code/Goose as subprocesses, and interoperate with the broader Nostr ecosystem (gitworkshop.dev, ngit, Chachi, 0xchat) for identity, git, and messaging. Arc can do none of this — its only inter-system surface is its own gateway adapters (Slack/Telegram/Mattermost), which are one-way inbound message bridges, not agent-to-agent or tool-to-agent protocols. This is not "behind by a feature" — it's an entire missing interop layer that Buzz treats as core architecture ("Protocol-native... No runtime coupling", VISION_AGENT.md:59).

## (c) What Arc must build, in order

1. **MCP client in `arcgateway`** (per ADR-018's own escape hatch: "community can write MCP as an adapter without core changes") — an `AdapterBase`-style MCP host that spawns stdio/HTTP MCP servers, lists tools, and surfaces them through `ToolRegistry` via the already-defined but unused `ToolTransport.MCP` path. This is the highest-leverage, lowest-risk item since the enum and config model already exist.
2. **MCP server** exposing Arc's own tool surface (equivalent of `buzz-dev-mcp`) so external agents (Claude Code, Codex, Zed) can call Arc tools — unlocks Arc as a tool provider, not just a tool consumer.
3. **ACP agent adapter** so `arccli`/`arcui` sessions can be driven by any ACP host (Zed, JetBrains) — reconsider ADR-018's ACP exclusion once this is built, since "ACP still evolving" is now less true than in April 2026.
4. **AGENTS.md** at repo root (trivial — convert/symlink from `CLAUDE.md`) for cross-tool contributor compatibility.
5. Nostr/git-signing is lower priority for Arc's federal-first identity model (see (d)).

## (d) Should Arc adopt ACP and/or Nostr, or stay MCP-only?

**MCP client: yes, build it now.** It's the dominant tool-interop standard, ADR-018 already flags it as the first reconsideration trigger, and the risk is bounded (adapter pattern, no core trust-boundary change).

**ACP: build the agent side, skip the host side for now.** Arc's CLI/TUI/Web already cover dev UX (ADR-018's own rationale); adding ACP-agent support is pure upside for external-editor interop with low protocol-surface risk since Arc, unlike Buzz, doesn't need to *drive* other coding agents — Arc's model is one integrated harness, not a multi-agent bridge.

**Nostr: no.** It's a strong bet for Buzz because Buzz's product *is* federated identity/relay/git infrastructure for community-run agent swarms — "the relay is the workspace" fits that thesis. For Arc, whose stated north star is FedRAMP/NIST 800-53/CMMC federal deployment (ADR-019, project memory), an open federated pubkey relay is close to the opposite of the four-pillars model (signed artifacts, `arctrust` DID, fail-closed policy, tamper-evident audit chain) — introducing an unauthenticated/pseudonymous federated transport as a control-plane dependency would be a step backward for the compliance posture that is Arc's actual differentiator. Nostr is a weaker interop bet for Arc than for Buzz specifically because their target users differ: Buzz targets open communities; Arc targets regulated enterprises/agencies that need closed, auditable trust chains, not open federation.

## (e) Where Arc does better

Arc's `arcgateway-{slack,telegram,mattermost}` adapters give it real, shipped inbound-platform integrations that Buzz has no equivalent to (Buzz's outward surface is the Nostr relay itself, not third-party chat platforms). Arc's tool registry already separates transport concerns (native/MCP/HTTP/process) with a policy/audit/classification layer (`tool_registry.py:91-598`) that MCP tools would plug into for free once a client is built — Buzz's MCP client (`mcp.rs`) has no equivalent per-tool policy-pipeline integration, relying instead on process isolation and byte-budget truncation. Arc's four-pillars identity/audit model is a stronger foundation for *safely* adding MCP/ACP later than Buzz's model would be for adding Arc-style compliance later.

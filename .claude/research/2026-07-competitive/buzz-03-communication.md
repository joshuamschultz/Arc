## (b) The fundamental architectural difference

**Buzz: one signed event log is the workspace.** There is exactly one data model (a Nostr event: id/pubkey/kind/tags/content/sig) and every feature — chat, reactions, workflow steps, job dispatch, approvals, presence, push leases, even git pushes — is a new `kind` integer over that same log, stored in one Postgres event table, delivered through one pub/sub fan-out, searchable in one FTS index. "New message type? New kind integer. Zero breaking changes" (`VISION.md:75`). The relay's entire job is: verify signature → apply kind-specific access rule → store → fan out. Agents are not a different kind of participant; they hold the same keypair primitive as humans (`VISION.md:85-94`) and their entire lifecycle (job request/accept/progress/result) is legible in the *same* audit/search surface a human's chat history lives in.

**Arc: purpose-built subsystems that interoperate through message-passing, not a shared substrate.** ArcTeam owns inter-agent messaging (a `Message` Pydantic model over NATS JetStream streams), ArcStore owns tasks (a distinct `Task` model with its own collection, its own status machine, its own reliability watcher) and approvals (another distinct model, another collection), and audit is a fourth system (`arctrust.audit`) that all of these *emit into* rather than *are*. Each subsystem is deeper and more hardened in its narrow domain — Arc's task reliability engine (retry/backoff/dead-letter/DAG deps) and its approval spoof-resistance (operator-key-bound grants that never travel over chat) both exceed what Buzz has shipped in the equivalent surface — but there is no single log an operator, a compliance auditor, or a search query can point at and say "this is everything that happened." Cross-system correlation (did this task's completion trigger this approval which produced this chat message) requires joining three schemas by convention (shared `session_id`/`actor_did` strings), not by structural guarantee.

The practical consequence: Buzz's model unifies *for free* — new features are just new kinds, and every kind automatically inherits audit, search, and access control. Arc's model requires deliberate wiring *per subsystem* — which is exactly the "producers unwired" failure pattern already logged in this project's memory (`project_producers_unwired_pattern.md`): correct predicates shipped with dead activation wiring, because every new capability needs its own plumbing rather than falling out of an existing substrate.

## (c) What Arc should adopt

1. **A single append-only event log with a kind registry**, even without going full-Nostr/relay. Collapsing `Message`, `Task`, `PendingApproval`, and audit events into one signed, kind-tagged event stream (each currently a hand-rolled Pydantic model over its own collection) would let Mission Control, approvals, and chat all live in one searchable, auditable timeline — which is exactly the FedRAMP/NIST AU-family audit story Arc is already trying to tell, but currently tells three times.
2. **Reactions/mentions as a structural join primitive, not a convention.** Buzz's persona `triggers.mentions` ties channel membership to the mention mechanism (`persona.rs:129-139`); Arc's mention system (`mentions.py`) is disconnected from `Channel.members` (`messenger.py:190-207`) — two independent gates a caller must reason about separately. Unify them.
3. **Push notifications.** This is a flat-out capability gap, not a design tradeoff — Arc has zero mobile/push story. If Arc ever needs an operator or approver to be reachable off-machine (e.g., resolving a SPEC-035 approval from a phone), `buzz-push-gateway`'s pattern (device-attested endpoints, signed leases, sanitized delivery outcomes) is a reasonable reference architecture to build toward, scoped to federal-appropriate channels (not APNs in a SCIF, but the attestation/lease-scoping pattern generalizes).
4. **Presence as a first-class enum shared across transports** (`PresenceStatus` in `presence.rs:5-18`) — cheap to add, useful for arcui's live trace dashboard and for knowing whether a mentioned agent is actually running.

## (d) What Arc does better

- **Approval gates that actually work.** Buzz's WF-08 approval suspend/resume is explicitly unimplemented (`executor.rs:663`, `VISION.md:125`) — a workflow hitting it just fails. Arc's SPEC-035 mechanical approval is shipped, race-safe, and cryptographically bound to the operator's key so chat can't forge it (`approvals.py:1-9,120-153`). Buzz's "👍 reaction and ships" pattern (`README.md:93`) is a narrative convention riding a generic reaction kind — good UX, zero enforcement.
- **Task reliability.** Arc's Mission Control has retry/backoff, dead-letter, DAG dependencies, and a background reliability watcher (per `project_task_reliability_engine.md`); Buzz's job-kind events (43001-43006) give a lifecycle trail but no evidence of equivalent retry/reliability machinery.
- **Prompt-injection-aware task construction.** `tasks.py:37-63` sanitizes task text against a dozen injection patterns and tier-gates external references (URL/email) before a task is even created — a defense Buzz's event-kind model doesn't appear to apply to job-request content.
- **Classification-aware, no-write-down messaging.** `messenger.py:209-279` enforces recipient-clearance dominance on every send, fails closed at federal tier on unresolvable clearance — a control with no Buzz analogue (Buzz's access model is channel membership only, `VISION.md:35-46`).

## (e) Gateway-per-platform vs own-the-workspace — honest argument

**For enterprise/federal, Arc's gateway-per-platform bet is the more defensible near-term strategy, but it is a ceiling, not a floor, and Buzz's bet is the one that wins if either company is still around in five years.**

Own-the-workspace is a genuinely larger and riskier bet: Buzz is proposing to *replace* Slack/Discord/GitHub/Jira for a community, which means winning a change-management fight enterprises are usually allergic to, and it concentrates an enormous amount of attack surface (chat + code + voice + workflows + push, all through one relay) into a single component that must now clear FedRAMP/CMMC on its own — Buzz's own docs candidate multi-tenant isolation as "proven... via TLA+/Tamarin," which signals they know this is the hard part, not a solved one. A SCIF customer is not going to swap Mattermost for a startup's Rust relay next quarter regardless of how elegant the event model is.

Arc's gateway approach is lower-risk precisely because it doesn't ask anything of the customer's existing stack — it sits beside Slack/Mattermost/Telegram, inherits their existing ATO, and lets Arc's differentiation live entirely in the agent layer (identity, policy, audit) rather than in owning the surface. That is the right shape for a "premier federal agentic harness" that has to slot into environments that already picked their chat tool for reasons unrelated to AI.

But the ceiling is real: gateway adapters can only ever be as expressive as the platform they're wrapping. Arc's Slack/Telegram/Mattermost adapters cannot give an agent a signed, kind-typed event log, a job board, or a workflow-with-approval-gate that composes with chat the way Buzz's model does natively — because those platforms weren't built with agents as first-class members. If Arc's long-term ambition includes things like "an agent's job history is queryable in the same audit trail as the conversation that spawned it" or "a workflow approval and a chat reaction are the same primitive," that requires Arc to eventually own a piece of the substrate the way Buzz does, at least for the multi-agent-to-agent layer (arcteam) even if the human-facing chat surface stays gateway-fronted. The event-log idea is worth stealing structurally now (recommendation (c)(1)) precisely so Arc isn't stuck retrofitting it under enterprise deadline pressure later.

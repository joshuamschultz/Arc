**Key honest answer to Q6 (identity/signing on inter-agent messages):** Outside of **A2A's Signed Agent Cards** (protocol-level, cross-vendor, adoption ~150 orgs but "not universal"), **no coding-agent product surveyed (Goose, Claude Code, OpenCode, Grok Build, Codex, Devin, OpenHands, Cline, Hermes, OpenClaw) documents any cryptographic identity, signing, or authorization on agent-to-agent messages.** Isolation there is by *architecture* (separate VMs/sandboxes/worktrees), not by *authenticated identity*. This matches Arc's own differentiator: mTLS + Ed25519-signed inter-agent messages (ASI07) is not something any competitor ships today. ## (c) Per-product deep notes

**Block Goose** — Evolving from single chat agent into a "meta-agent orchestrator" managing sessions/workflows/recipes/subagents ([goose-docs.ai](https://goose-docs.ai/blog/2026/05/05/goose-as-conductor/), [block-goose.mintlify.app](https://block-goose.mintlify.app/concepts/agents)). Subagents run "sub-recipes" separately from the main recipe. Can delegate not just to its own subagents but to *external* agents (Claude Code, Codex, Amp) via ACP — Goose positions itself as an agent-agnostic conductor, not just a single-vendor agent. Explicit design statement: "Delegates only know what you tell them. They don't share context with each other or with the parent session" — i.e., Goose deliberately uses fresh/isolated context per delegate, not full inheritance, as a poisoning-avoidance strategy. Concurrency model is phase-based ("reads can be parallel, writes should be sequential") rather than lock-based. Community extension "Goosetown" orchestrates "flocks" (researcher/writer/worker/reviewer roles). [goose-docs.ai/blog](https://goose-docs.ai/blog/2026/05/05/goose-as-conductor/), [pulsemcp.com](https://www.pulsemcp.com/building-agents-with-goose), [maxamillion.sh](https://maxamillion.sh/blog/stop-building-agents-start-harnessing-goose/), [github.com/aaif-goose/goose discussion #6973](https://github.com/aaif-goose/goose/discussions/6973)

**Claude Code Agent Teams / Managed Agents** — Shipped experimentally Feb 2026 alongside Opus 4.6. Core distinction from classic subagents: teammates talk to *each other*, not just to the lead, via a **mailbox** (direct + broadcast) and a **shared task list** with states (pending/in-progress/completed) and dependencies. Each teammate gets the same static project context (CLAUDE.md, MCP servers, skills) plus the lead's spawn prompt, but explicitly **not** the lead's conversation history — a deliberate fresh-context boundary per teammate, similar in spirit to Goose's delegate isolation. Separately, Claude Code v2.1.49 (Feb 2026) shipped built-in `--worktree` support: auto-created worktree + auto-suffixed branch per parallel session, cleaned up if no changes made — this is the concurrency-control primitive, though it's not described as tied specifically to Agent Teams in the sources found. Classic subagents (Task tool) remain single-session, isolated-context, structured-summary-return, matching Anthropic's own published multi-agent research system architecture (orchestrator + isolated-context workers returning 1,000–2,000 token summaries). Steering: real-time mid-generation steering is a **known, still-open gap** — four separate open GitHub feature requests as of mid-2026 (#64624, #30492, #25845, #50246); today, messages sent during generation are queued, not injected, and Escape discards all in-flight work rather than steering it. Plan Mode is the primary pre-action approval gate. **OpenCode (SST)** — Directly ported Claude Code's Agent Teams pattern (acknowledged by the community port itself: "Porting Claude Code's Agent Teams to OpenCode"). Differentiator: mixes models/providers per teammate in the same team (Claude Code Agent Teams is same-account/model). Architecture per DeepWiki: event-driven messaging, append-only JSONL writes for inbox persistence, peer-to-peer, two-level state machine, fire-and-forget spawn. Subagent roles ship as named presets: Plan (primary, file edits + read-only analysis), General (full tool access), Explore (read-only codebase search) — this maps closely to Arc's own module/skill separation philosophy. **Grok Build (xAI)** — Launched May 14, 2026, in beta. Uses Agent Client Protocol (ACP) for third-party tool integration — same protocol Goose uses to delegate to external agents. **OpenAI Codex** — Cloud-sandboxed, one task = one isolated sandbox with its own git state; this is how it avoids concurrency collisions (isolation by construction, not locking). ## (d) Patterns clearly winning in 2026

1. **Git-worktree-per-task/per-agent is the converged concurrency primitive.** Claude Code (native `--worktree`, v2.1.49), OpenCode, and Hermes Kanban all independently landed on the same mechanic: isolate each parallel agent in its own worktree + auto-named branch rather than locking files. Teams reportedly run 4–8 concurrent worktrees per developer by mid-2026. This is a strictly stronger pattern than Arc's current file-collision-detection approach in some ways (isolation by construction beats detection-after-the-fact) — worth evaluating for arcrun's parallel task execution.

2. **Isolated/fresh context per delegate, with structured-summary handback, is the dominant anti-poisoning design — not full context inheritance.** Goose ("delegates don't share context with each other or the parent"), Claude Code Agent Teams (fresh context + spawn prompt, no lead history), Anthropic's own orchestrator-worker research system (1,000–2,000 token condensed summaries), and Amp's subagents ("consolidating knowledge to prevent repeated explanations") all converge on the same idea: minimal-necessary-context out, structured-summary back. Full context inheritance is explicitly avoided as an anti-pattern industry-wide.

3. **Isolation-by-construction (VMs/sandboxes/worktrees) is trusted far more than any authorization layer.** Every product surveyed (Codex cloud sandboxes, Devin's per-child VM, Claude/OpenCode/Hermes worktrees) solves concurrency and blast-radius by giving each agent its own execution environment, not by permissioning shared state. This validates Arc's shared-nothing-per-agent architecture principle directly.

4. **Human-facing "receipts," not raw logs, is emerging as the trust UX.** Google Antigravity's Artifacts (plans/screenshots/browser recordings as reviewable objects) and Cursor's diff-review-before-merge are both explicit bets that humans verify *artifacts of work*, not transcripts. This is a stronger pattern than Claude Code's current todo-list-only surfacing and is worth benchmarking arcui's task/timeline views against.

5. **Slack/Teams-as-the-human-channel has become table stakes, with agent-initiated cross-channel reach as the frontier.** Devin (Slack/Teams task intake), Cursor (Slack-launched agents that read/post across channels), and third-party notifier glue (Agent Notify, coding-agent-notifier bridging Claude Code/Codex/Gemini CLI/OpenCode to push+desktop) show the market has settled on "meet humans where they already work" — but note this is largely bolted on via third-party tools, not native, for most products except Cursor and Devin.

## (e) Unsolved problems everyone still has

- **No one signs or authenticates inter-agent messages at the product level.** A2A's Signed Agent Cards are the sole cross-vendor exception, and even there, authorization (not just identity) is explicitly left unspecified by the spec. Every coding-agent product surveyed relies entirely on process/VM/worktree isolation instead of cryptographic trust between agents — this is a genuine, verified gap and a real differentiator for Arc's DID + Ed25519 + PolicyPipeline approach (ASI03, ASI07).
- **Real-time mid-task steering is still broken industry-wide.** Claude Code's four open feature requests on this exact problem (queue vs. inject, Escape-discards-everything) suggest no one has actually solved "redirect an agent without losing its in-flight work" — an open UX/architecture problem, not just a Claude Code gap.
- **No formal adversarial verification / judge-panel pattern in production coding agents.** The closest things found are Codex's "second agent reviews the first agent's diff" and Devin's coordinator "resolves conflicts, compiles results" — both single-reviewer, not adversarial panels or test-gated handoffs. The LLM-as-judge research (JUDGe 2026 workshop, pass^k calibration against 500+ human-gold cases) is active in academia but not yet a shipped feature in any product surveyed.
- **Cross-agent communication mechanics are largely undocumented even by the vendors themselves.** Goose's own blog post about being a "conductor" explicitly does not specify its transport/handoff mechanism; Claude Code's Agent Teams guide omits message format, verification, and collision-detection details. The market is shipping the *feature* (multi-agent coordination) faster than it is publishing the *architecture* — meaning competitive intelligence here has an inherent ceiling without source access.
- **Notification reliability is inconsistent and product-specific.** Cursor's own docs admit Slack completion DMs don't fire for long-running or GitHub-initiated agents — even the most Slack-native product has gaps in the agent→human "I'm done" signal.
- **Multi-human collaboration on a single agent session (not just human↔agent) is immature.** The most mature *pattern* found — LiveKit's voice-AI hold+brief+merge handoff — has not been mirrored in any coding agent surveyed; Hermes' Kanban ("any profile or human can read/edit a row") is the closest coding-agent analog but is framework-level, not a polished UX.

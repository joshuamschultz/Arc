# Execution reliability research (static audit, 2026-09-23)

> Initial findings are a research snapshot against local `1850fd3a`. Later patch evidence may be appended. See [the implementation record](../business-reliability-program.md#implementation-record) for current fixes and final verification.

Scope: hosted/server behavior across ArcAgent, ArcRun, ArcLLM, ArcTeam, ArcGateway and ArcPrompt. No source edits or quality gates were run. Findings below are **static-proven mechanisms**, not claims that a production incident followed exactly this path. The repository began clean. Root and package `AGENTS.md` were read. Severity reflects business impact if the path is exercised.

## Priority findings

1. **Critical — Slack events can be irretrievably marked seen before delivery. Owner: ArcGateway.** `_DedupStore.record_or_skip` commits a row (`packages/arcgateway/src/arcgateway/adapters/slack/adapter.py:100-107`), and `_handle_inbound` calls it at :471-493 before auth, media conversion and `await self._on_message(inbound)` at :495-543. If the gateway is cancelled, crashes, loses ArcStore, or `_on_message` raises between those points, a Slack retry with the same event ID is discarded for 24 hours. This can explain missing messages or images even though media conversion itself exists. Fix by recording a durable incoming event and processing state before acknowledging, then transition to delivered only after the agent handoff is durable; duplicate IDs must resume pending work. Acceptance: inject failure after dedup claim and before handoff, replay same Slack event after process restart, observe exactly one completed agent turn and reply; inject crash after delivery commit, observe no duplicate turn. Keep signed authorization and audit at every transition.

2. **Critical — channel inbox acknowledges a wake, not an answer; failed reply is swallowed. Owners: ArcTeam + ArcAgent.** `MessagingService._dispatch` acks once `handler(message)` returns (`packages/arcteam/src/arcteam/messenger.py:814-830`). The handler calls `_wake_on`, whose normal `deliver_fn` may open an asynchronous tracked run and return (`packages/arcagent/src/arcagent/modules/messaging/capabilities.py:215-285`; `packages/arcagent/src/arcagent/core/agent_dispatch.py:540-547`). The eventual finalizer logs and suppresses run/commit/post-response failures (`agent_dispatch.py:550-583`); channel reply hook logs and suppresses send failure (`messaging/capabilities.py:444-473`). Thus the transport can be acked while the answer never reaches the channel. Fix with a durable, correlated inbox-work/reply-outbox state machine: received -> accepted run -> terminal result -> reply pending -> delivered, with idempotent retry, visible terminal failure and explicit ownership. Do not hold a NATS ack open for an entire LLM run. Acceptance: kill worker after accepted wake, fail model, fail channel send, restart and reconcile to one reply or actionable failed state; prove no unauthorized replay.

3. **High — live messaging can silently isolate a hosted agent on an in-memory backend. Owner: ArcAgent messaging.** On startup `messaging_inbox_loop` tries the NATS upgrade once and catches any exception, then continues on the in-memory backend (`packages/arcagent/src/arcagent/modules/messaging/capabilities.py:957-969`). A temporary broker outage during agent start leaves a running agent disconnected from the shared fleet even after broker recovery; this loop does not retry the upgrade. Fix through supervised reconnect to the configured durable backend, explicit degraded health, and no claim of fleet readiness until the shared bus subscription is active. Acceptance: start agent while NATS is down, restore NATS without restarting agent, send signed DM/group message, verify one response; verify degraded and recovered signals. The existing `MessagingService` durable consumer itself is substantial and should be preserved.

4. **High — workflow host can die while gateway remains healthy. Owner: ArcGateway.** `RunnerHost.start` launches a detached task (`packages/arcgateway/src/arcgateway/workflow_runner_host.py:94-112`). `_run` catches an unexpected exception, logs it, closes the runner and clears `_active` (`:114-132`); no supervisor restarts it or makes GatewayRunner fail readiness. `start_runner_host` is called during bootstrap, not continuously (`:262-305`). ArcFlow's internal tick loop does catch ordinary tick failures (`packages/arcteam/src/arcteam/workflow/runner.py:345-402`), so the gap is a fatal exit outside that loop, not every store blip. Fix a gateway-owned supervisor that restarts with backoff and monitors progress/lease health; expose per-run staleness and fail readiness if no runner can advance. Acceptance: inject a fatal runner exception and a host process restart with active runs, verify lease fencing and eventual progression exactly once; verify alerts when recovery repeatedly fails. Preserve ArcTeam deterministic runner and lease.

5. **High — the missed-message sweep deliberately gives up after one failed wake and only scans a finite tail. Owner: ArcAgent messaging.** `run_once` puts an ID into `st.swept` before calling `deliver`, then suppresses errors without removing that ID (`packages/arcagent/src/arcagent/modules/messaging/sweep.py:119-144`). This proves a transient delivery error cannot be retried in the same process. `find_missed` sees only the last 200 channel messages (`:32-34, :105-115`), so sustained traffic can push a missed question out of reach. A restart clears `swept` (`messaging/_runtime.py:78-81`), which may create another attempt, but restart is not an operational retry policy. Fix bounded durable pending/attempt states with retry schedule and a query by unanswered status rather than newest-N only; assign a dead-letter owner after max attempts. Acceptance: one transient wake failure then recovery without restart yields one answer; over 200 newer posts cannot hide an unanswered human question; restart does not duplicate a successful reply. Existing unit tests explicitly pin the current no-retry behavior (`packages/arcagent/tests/unit/modules/messaging/test_context_filter_and_sweep.py:256-264`) and must be revised deliberately.

6. **High — Slack reply delivery is not bound to durable completion of the inbound event. Owner: ArcGateway.** The dedup row is committed before `self._on_message` (:471-543), while the gateway executor streams asynchronous output (`packages/arcgateway/src/arcgateway/executor.py:322-402`) and `StreamBridge` sends or edits platform messages independently. A process crash after model completion but before final send has no shown replayable reply-outbox tied to the Slack event ID. This is distinct from #1's loss before agent handoff and should be validated end to end. Fix by correlating platform event ID, agent run ID, and channel delivery ID in the durable state machine; use the platform's idempotent update/known message ID where available. Acceptance: crash at each boundary (receive, run accepted, model complete, placeholder sent, final edit) and verify one final visible reply or explicit failed state. The source inspection proves the separate boundaries, but absence of another outbox elsewhere remains **unverified** pending a full ArcStore/gateway trace.

7. **Medium — tracked asynchronous runs lose the streaming path's pre-loop trace correlation. Owner: ArcAgent.** Streaming dispatch allocates one run ID before `build_run_context`, wraps prompt assembly in `request_context(run_id)`, and passes that ID to ArcRun (`packages/arcagent/src/arcagent/core/agent_dispatch.py:375-429`). `start_tracked_run` builds the prompt before `arcrun.run_async`, with no corresponding request context or explicit run ID (`:498-535`). The prompt snapshot supports `request_id` (`packages/arcprompt/src/arcprompt/snapshot.py:64-89`), but this path does not provide one. Likely effect: prompt/memory assembly events for inbox-opened runs are hard to connect to the eventual run trace; the exact stored trace shape is **unverified**. Fix one run ID allocated before prompt assembly and propagated through ArcPrompt audit, telemetry, ArcRun and session metadata on both paths. Acceptance: a channel-triggered tracked run yields a single correlation ID joining prompt provenance, strategy, model/tool traces, session and delivery events, including failure.

8. **Medium — multi-instance gateway execution is explicitly unimplemented. Owner: ArcGateway.** `NATSExecutor.run` raises `NotImplementedError` (`packages/arcgateway/src/arcgateway/executor_nats.py:17-37`); `AsyncioExecutor` is in-process (`executor.py:236-280`). For a hosted installation with multiple gateway replicas or separately scaled agent workers, this is an architectural deployment limit, not evidence that the current single-instance deployment is broken. Verify actual deployment topology first. Acceptance for future multi-instance mode: one message consumed by one authorized worker, lease/fence across worker loss, durable result and reply, no split-brain bot polling. Do not add this merely to fix single-instance reliability.

## Follow-up on stacked LLM calls, images, pulse, and prompts

9. **Critical — default ArcLLM call queue is bypassed by streaming turns. Owner: ArcLLM.** QueueModule overrides only `invoke` (`packages/arcllm/src/arcllm/modules/queue.py:73-132`). The inherited `BaseModule.invoke_stream` directly forwards to the inner provider (`modules/base.py:110-118`), and ArcRun's ReAct path prefers `invoke_stream` (`packages/arcrun/src/arcrun/strategies/react.py:460-481`). The stock config enables QueueModule (`packages/arcllm/src/arcllm/config.toml:113-121`), but that does not bound simultaneous provider streams, their queue depth, or their provider send time. A separate ArcRun absolute deadline may still bound the whole run; it does not make QueueModule's protections effective. **Most bounded first local implementation:** make QueueModule gate the entire async stream, with semaphore release on complete/cancel/generator close, a send-time timeout covering first and subsequent deltas, and the same stats/OTel semantics as `invoke`. Contract tests must use a real `load_model` wrapper plus concurrent ReAct streaming calls; stall before first token and mid-stream; cancel waiting and active calls; ensure slots/counters recover. This fixes an immediate high-impact defect while the larger durable queue is designed.

10. **High — SPEC-014 queue cannot satisfy the new hosted queue product requirement. Owner: ArcLLM core contract plus ArcUI/ArcCLI surfaces.** SPEC-014 README expressly defines an internal, per-adapter, per-process semaphore with no API/UI. `QueueModule` keeps waiters/counters only as object fields (`modules/queue.py:61-71`) and has no waiter identities, durable state, tenant scope, queue-wait deadline or cancel operation. `queue_stats()` returns aggregate counters only (`:142-158`). ArcUI exposes a read-only `/api/queue` over `app.state.queue_modules` (`packages/arcui/src/arcui/routes/stats.py:126-138`); server initializes that list empty (`server.py:708`) and offers a module collection seam (`:812`), but no queue list/cancel controls were found in ArcUI or ArcCLI. **Static proof:** current queue is not durable or operator-controllable. **Hypothesis needing integration check:** the endpoint may show `[]` in actual deployment if the module collection hook is never wired; inspect runtime app state to confirm. Design a separate durable admission/call-state seam owned by ArcLLM, with caller/tenant identity, fair scheduling and per-tenant quotas, absolute enqueue deadline plus provider timeout, cancellation and uncertainty states. ArcUI and ArcCLI should use one authenticated control API, enforce policy/audit on list/cancel/retry and expose queued/active/timed-out/uncertain history. On crash, do not blindly reissue a call whose remote acceptance is unknown; reconcile by provider idempotency where offered or surface uncertainty. Acceptance includes two tenants under load, worker crash/restart, cancellation before dispatch and during provider stream, stale waiter timeout, fair progress, and no cross-tenant visibility.

11. **High — ArcUI image uploads are classified as generic files and never become model image blocks. Owners: ArcUI + ArcGateway media contract + ArcAgent translation.** `upload_attachment` passes `kind="file"` for every multipart upload (`packages/arcui/src/arcui/routes/attachments.py:69-77`). MediaStore detects and validates the MIME but persists the supplied `kind` unchanged (`packages/arcgateway/src/arcgateway/media_store.py:309-347`); gateway web claim forwards that stored kind (`bootstrap.py:244-269`). Agent `PartTranslator` emits an `ImageBlock` only for `kind=="image"`; a non-PDF file becomes a readable filename line (`packages/arcagent/src/arcagent/parts.py:127-156`). OpenAI/Anthropic adapters do support `ImageBlock` (`packages/arcllm/src/arcllm/adapters/openai.py:240-254`, `anthropic.py:86-99`), so the loss is upstream. Derive canonical kind from validated detected MIME at the MediaStore boundary and preserve verified kind through manifest/claim. Acceptance: upload PNG/JPEG via real ArcUI route, send attachment ID over web chat, inspect provider request body for image data; malformed MIME and cross-session claims remain rejected. This is a direct, bounded, safe candidate for first local fix.

12. **High — pulse and scheduler stop after five whole-tick errors without a supervising restart. Owner: ArcAgent module lifecycle.** Pulse's `FailurePolicy(max_consecutive=5)` exits `_timer_loop` and sets `_running=False` (`packages/arcagent/src/arcagent/modules/pulse/engine.py:149-174`). Scheduler has the same pattern (`modules/scheduler/scheduler.py:441-471`). They log critical at threshold, but no auto-restart appears in these engines. A durable server process can therefore remain nominally up while scheduled activity is down. Repeated failure may reflect a persistent bad state, so restart with bounded backoff and degraded health must avoid a tight failure loop. Acceptance: inject five failing ticks, restore dependency, verify engine resumes without restarting agent and ArcUI reports outage/recovery; scheduled side effects require idempotency and fencing. Task dispatch and reliability watcher, by contrast, have self-contained loops that catch tick errors (`modules/tasks/capabilities.py:1378-1417`), so their failure needs a different trace.

13. **Medium — prompt provenance correlation differs from missing session/trace records. Owner: ArcAgent + ArcPrompt.** Streaming dispatch already allocates a run ID before prompt assembly and binds `request_context(run_id)` (`packages/arcagent/src/arcagent/core/agent_dispatch.py:375-429`). Tracked inbox runs call `build_run_context` before ArcRun allocates its handle (`:498-535`). `snapshot_run_prompts` accepts `request_id` (`core/prompt_context.py:101-116`) but `_run_prompt_resolve` omits it (`agent_dispatch.py:163-183`), even for streaming dispatch. This is a provenance joinability defect; it does **not** prove prompt bodies, session JSONL, or LLM traces are absent. Session records are written by `session.append_message` (`:385`, `:512`); trace store is constructed under `<agent_root>/traces` (`core/model_manager.py:303-345`). A failed run before assistant append can leave only a user turn, while a model error can leave an error trace. Acceptance: one run ID joins prompt snapshot audit, session, model trace and gateway delivery for both dispatch paths, and the UI explicitly distinguishes absent data from inaccessible/mismatched data.

14. **Medium — web chat replay buffer is process-local and only 50 frames. Owner: ArcGateway.** Browser output is queued per socket and sent asynchronously (`packages/arcgateway/src/arcgateway/adapters/web.py:1-20, :308-323`); the replay ring is a `deque` of 50 frames per chat (`:57-70, :155-160`). Gateway restart loses the replay ring, so a disconnected browser cannot recover live frames solely through this mechanism. Session history may recover completed text, but no proof yet that a partial run or its terminal status is reconstructed. Test restart while a turn is streaming, reconnect with `since_seq`, and compare browser state against durable session/trace/run state. This is **static-proven transient replay storage**, with exact user impact deployment-dependent.

Email note: no in-tree first-party Gmail/IMAP polling module was found under ArcAgent or ArcGateway in this bounded search. Email behavior likely belongs to connector/extension paths and remains unverified; inspect the installed hosted connector inventory and activation lifecycle before claiming a specific email failure.

## Local ArcLLM queue fix verified (2026-09-23)

Finding 9 above describes the **pre-fix** behavior. The local main checkout now gates `invoke_stream` through the same queue admission, accounting, and capacity as `invoke`. Its timeout bounds each provider await against one monotonic send-time deadline and never spans a yielded delta, so slow consumer code is not cancelled by the provider timeout. Early close, cancellation, provider failure, and timeout release the slot. `max_queued=0` now allows an immediate free slot and rejects only when all slots are occupied. Provider-originated `TimeoutError` is preserved and not counted as a queue timeout for both invoke shapes.

An owned-stream context closes each delegated iterator through BaseModule, FallbackModule, RoutingModule, and TelemetryModule. A configured `load_model` chain test exercises early outer close with telemetry/fallback/routing enabled and confirms provider closure, queue slot release, and no completed telemetry spool row. A separate test proves the stock `load_model("anthropic")` configuration includes QueueModule and counts a streaming call. A cleanup failure does not replace the original provider failure; the cleanup log contains only the exception type, not its payload. Tests also cover mixed stream/non-stream capacity, backpressure, first/midstream timeout, slow consumers, cross-task `anext`/`aclose`, and active/waiting cancellation.

Fresh validation: `packages/arcllm/tests` **1471 passed, 1 skipped**; strict mypy **57 source files clean**; Ruff lint and format checks clean for the seven changed ArcLLM files. This patch is process-local and does **not** implement the requested durable, fair, tenant-aware queue or ArcUI/ArcCLI list/cancel controls. Those remain the design work in finding 10.

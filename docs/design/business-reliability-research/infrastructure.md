## DGX observations and limits

Root filesystem 5% used; 114 GiB RAM available. These are current observations and **do not disprove last night's outage**. The installed runtime symlink resolves to `~/.arc/runtime/0.5.0-130403ed`. That suffix is absent from local Git objects; exact deployed ancestry and code parity remain unverified. The initial status diagnostic unexpectedly exposed command-line viewer/operator tokens in tool output; this report omits them. They need rotation through the authenticated operator workflow. The exposure mechanism is static-proven at `deploy/systemd/arc.service:29`.

The NATS child process began Sep 21 07:36:10 CDT, three seconds after the app. It remained the same process across last night's Sep 22–23 incident window. Therefore a NATS **server death is unlikely to explain that specific incident**, despite the server supervision defect below. Client connection/consumer recovery or an unrelated timeout path needs investigation.

For Sep 22 18:00–Sep 23 09:00 CDT, a sanitized tail of 20,000 `arc.service` journal lines had 194 NATS-plus-failure/connection pattern matches, 1,896 timeout mentions, 3 memory-write-failure pattern matches, and 5 task-failure pattern matches; zero `connection refused`, `broker unavailable`, or Postgres-failure pattern matches. A wider 30,000-line tail had 320 NATS-client-error-pattern lines and 59 consumer-error-pattern lines, with zero NATS-server-unavailable or JetStream-error matches. These are broad regex line counts, not distinct incidents or confirmed causes. The sampled tail may omit earlier lines. More precise component event and timestamp correlation is needed. No raw lines were printed or retained.

A 50,000-record incident-window sample found 2,526 literal `TimeoutError` lines concentrated at 02:00–06:00 CDT (865, 937, 154, 404, 134 by successive hour; 32 at 07:00). Of the 2,522 in a slightly narrower 02:00–08:00 sample, 2,496 had NATS client or JetStream client paths in nearby traceback context; 26 were unclassified. This implicates NATS client request/consumer behavior, **not a dead broker process**, but traceback proximity and sampling do not prove whether the client, server latency, event-loop stall, or request volume caused timeouts. ## Ranked findings

1. **Critical, static-proven: broker dies independently with no parent restart. Owner: `arcteam` broker seam plus `arcgateway` composition root/deploy.** `packages/arcteam/src/arcteam/nats_server.py:143-185` starts and checks NATS once; `ManagedNatsServer` at lines 110-140 only tears it down. `packages/arcgateway/src/arcgateway/broker_bootstrap.py:71-99` reports a startup snapshot. `deploy/systemd/arc.service:30-31` restarts only when the parent fails. Thus a later NATS child exit can leave `arc.service` running indefinitely, with messaging inaccessible and no auto-restart. DGX currently has the child, so this is a failure mechanism, not proof it happened last night. Fix with an owned broker lifecycle that detects child exit and recovers/reconnects or makes the supervised parent fail; preserve explicit ownership and do not kill a reused external broker. Prefer a separate broker unit/container for hosted deployments with an authenticated readiness contract. Acceptance: kill the owned broker in an isolated test deployment; within a bounded interval it is restored, durable JetStream state and consumers resume, affected operations report unavailable during outage, and audit/alerts capture transition. Repeat after days idle and network flap.

2. **Critical, static-proven: health and restart verdict are false-positive for dependency failure. Owner: `arcui`/`arccli` surface and deploy.** `packages/arcui/src/arcui/server.py:97-108` always returns `{status: ok}`. `packages/arccli/src/arccli/commands/restart.py:139-155` calls the app healthy on that HTTP 200 alone. `packages/arccli/src/arccli/commands/up.py:568-579` has a NATS TCP probe but lines 607-613 explicitly make service rows non-gating; TCP alone cannot prove JetStream. `deploy/cloud/docker-compose.yml:9-28` has no healthcheck. Fix separate liveness from readiness: bounded live JetStream request, critical agent/connector monitor task state, configured index read/write probe where safe, and per-tenant status through ArcUI. Keep public liveness minimal and gate detailed state by operator authorization. Acceptance: broker killed or index backend stopped while HTTP server survives => readiness fails and hosted supervisor/alert sees it; liveness remains meaningful; no secrets in diagnostics. NATS officially distinguishes `/healthz`, `/jsz`, and connection metrics: https://docs.nats.io/learn/monitoring/monitoring-endpoints .

2a. **Critical, static-proven: startup NATS blip permanently pins messaging to an in-memory bus. Owner: `arcteam` composition and `arcagent` messaging attachment.** `packages/arcteam/src/arcteam/composition.py:30-52` returns `MemoryBackend` when an initial NATS connect fails. `packages/arcagent/src/arcagent/modules/messaging/_runtime.py:189-215` then sets `live_backend_ready=True` for that fallback, and future calls exit before retrying. This is a direct mechanism for a connection that remains broken after broker recovery; it is not proven to have occurred last night because the app and broker processes predate the incident. Fix a typed degraded state and bounded reattachment through the public ArcTeam seam, preserving signed identity/audit; never mislabel memory fallback as live. Acceptance: start agent while broker is unavailable, restore broker without restarting agent, then exchange signed direct and group messages through durable JetStream; UI shows degraded then healthy.

3. **High, static-proven: one connector catalog exception permanently stops periodic sync. Owner: `arcagent` connected-data module.** `packages/arcagent/src/arcagent/modules/connected_data/service.py:265-271` creates one `_monitor_loop` task; lines 582-603 perform `await self._catalog.snapshot()` outside any exception boundary. Per-source exceptions are handled at lines 615-642, but a catalog/backing-store transient throws out of the monitor loop, which is never restarted. This fits connections/knowledge silently ceasing after idle but has not been observed on DGX. Fix a bounded supervised monitor that treats catalog failures as degraded, retries with backoff, emits audit/health state, and resumes from durable source checkpoints. Acceptance: fake catalog raises once/for N ticks, then recovers; monitor remains alive, resumes source sync, and ArcUI shows degraded then recovered; cancellation still stops promptly.

4. **High, static-proven: connection sync status can be transiently invisible and credential failure intentionally requires human repair. Owner: `arcagent` connected-data.** Runtime statuses and tasks are process-local (`service.py:247-255`); `start` opens stores once (`265-271`), and `_run_leased` returns degraded if store or ingest is absent (`644-652`). The monitor retries ordinary failures hourly by default (`229`, `582-603`), and terminal auth errors back off (`624-635`, `health.py:20-52`). Durable state restoration already exists (`service.py:709-757`) and must be retained; this is not a claim that *all* status is lost on restart. Fix persistent operator-visible source freshness/error telemetry and explicit credential renewal/reauth path per connector, plus a restart recovery test on real granted connections. Acceptance: expired OAuth or transient provider outage marks only that source degraded; renewal resumes automatically where supported; terminal revocation shows actionable ArcUI reauth and survives restart; successful sync becomes searchable through the agent.

5. **High, static-proven crash window in connected-source materialization; exact customer impact unverified. Owner: `arcmemory`/`arcstore` adjacent seams.** `packages/arcmemory/src/arcmemory/connected_data.py:488-537` writes document, memory, profile/blob, provenance, then object-state in separate operations; `_write_and_index_document` at lines 663-690 writes markdown then deletes/rebuilds index. A crash/error between those steps can leave source file and index/provenance disagreeing. Source cursor/page commit is separately durable and fenced in `packages/arcstore/src/arcstore/source_sync.py:126-158`; verify coordinator ordering before claiming data loss. Fix idempotent restart reconciliation from source-of-truth markdown/object versions, or a staged commit protocol, within existing public typed seams. Acceptance: fault-inject crash after each materialization step; restart either completes same object exactly once or visibly leaves it pending; cursor never skips an unsearchable object, authorization/provenance remain correct.

6. **High, static-proven security/operational defect: command-line tokens expose reusable credentials. Owner: deploy/ArcUI startup.** `deploy/systemd/arc.service:29` passes viewer/operator tokens as CLI arguments. Process status on DGX displayed their values unexpectedly during this read-only audit. This violates the root `AGENTS.md` credential and log constraints, and limits safe diagnostics. Fix private file-descriptor/credential delivery to the process without argv/env dump exposure; rotate current tokens through authenticated operator control. Acceptance: `systemctl status`, `/proc/.../cmdline`, journald, crash metadata and support diagnostics contain no reusable token; ArcUI auth and audited rotation remain functional. Do not embed secrets in health output.

7. **Medium, static-proven hosted path drift and missing readiness gate. Owner: deploy.** `deploy/cloud/cloud-init.yaml:66-96` embeds a second minimal Compose spec, while `deploy/cloud/docker-compose.yml:21-70` defines optional pgvector/profile/volume behavior. Cloud-init's inline spec lacks that Postgres service and healthchecks; changes to the maintained Compose file do not reach this provisioning path. Its startup readiness loop (`cloud-init.yaml:105-110`) checks only `/api/health`, and shell loop can exhaust without failing the `runcmd` step deterministically. Consolidate to one rendered Compose source and a bounded, failing readiness gate. Acceptance: provision from cloud-init and manual Compose against the same fixture; config parity, persistence mount, configured backend readiness, reboot and recreate survive; broken backend prevents “ready”/sales activation.

8. **Medium, static-proven coverage gap: no weeks-scale recovery gate. Owner: CI/deploy.** `.github/workflows/ci.yml:91-99` excludes `slow` tests; current focused restart tests include `packages/arcmemory/tests/integration/test_collection_index_retrieval.py`, `packages/arcstore/tests/integration/test_postgres_backend.py`, `packages/arcteam/tests/integration/test_nats_backend_server.py`, and broker unit tests. No discovered hosted multi-day soak/fault schedule. Add deterministic virtual-clock idle/resume tests, restart/fault matrix in CI, and a non-blocking staged 24–72h soak with bounded resources and telemetry, followed by restore drill before $20/month launch. Measure per-tenant delivery, sync freshness, vector coverage, restart recovery time, queue lag, error budget, and cost ceiling; cap and isolate tenant work so one agent cannot consume the node. This extends existing tests rather than replacing them.

## What is already implemented and should be preserved

- Persistent JetStream store dir via `arcteam.config.default_jetstream_store_dir`; DGX NATS process used an operator state path. `deploy/cloud/docker-compose.yml:25-26` mounts `/data`, and `Dockerfile:93,109-110` sets `HOME=/data`, so the current container design intends durable state. Do not claim it all writes to ephemeral image storage.
- NATS Python backend enables library reconnection after first connect (`packages/arcteam/src/arcteam/backends/nats.py:135-157`) and durable JetStream consumers (`:103-125`). Verify consumer re-subscription after broker restart before redesigning this seam.
- Connected-source leases, fencing, cursor commits, terminal auth backoff and persisted state restoration already exist. Fix supervision/reconciliation around them, not a second source-sync engine.
- Memory markdown is the source of truth, SQLite index disposable/rebuildable (`packages/arcmemory/AGENTS.md`); vector coverage/status probes exist (`packages/arcmemory/src/arcmemory/status.py:59-113`). Test actual recoverability, not only database file presence. SQLite WAL needs local-host storage and careful checkpoint/backup handling: https://www.sqlite.org/wal.html .
